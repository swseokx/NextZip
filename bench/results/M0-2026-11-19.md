# M0 실측 결과 — 2026-11-19

NextZip M0(기반·프로토타입) 게이트 측정. 벤치마크 코퍼스(텍스트·혼합)로 K1·K2·K4를 실측하고, 목표의 70%에 못 미치는 항목은 원인과 설계 수정안을 적는다.

## 1. 게이트 판정 요약

| 지표 | MVP 목표 | 70% 기준선 | NextZip M0 실측 | 판정 |

- CPU: Ryzen 5 9600X (6코어 12스레드), Windows 11 Pro 10.0.26300, **Defender 실시간 보호 켜짐**
- 빌드: Rust 1.100.0 (stable-x86_64-pc-windows-msvc), `--release` (thin LTO, codegen-units=1)

- 원시 데이터: `M0-2026-11-19-{text,mixed}.{json,md,log}`. 게이트 판정은 스펙의 절대 목표값으로 합니다.

## 4. 미달 항목 원인 분석

### 4.1 K2: zstd로는 LZMA 수준 압축률에 도달하지 못함

텍스트 셋에서 zstd 레벨을 끝까지 올려도 45.4%에 미치지 못합니다(M0 세션 중 별도 측정).

| 설정 | 압축률 | 속도 |
|---|---:|---:|
| zstd 9 | 48.7% | 약 90 MB/s (프로세스 내) |
| zstd 19 (2 MiB job, overlap log 6) | 46.4% | 약 38 MB/s |
| zstd 22 | 46.3% | 4 MB/s |
| zstd 19 + long distance matching (wlog 27) | 46.4% | 차이 없음 |
| zstd 19 + 확장자별 정렬 | 46.36% (정렬 없이 46.41%) | — |
| **LZMA2 프리셋 6, 단일 스트림 (Python `lzma` = liblzma)** | **45.40%** | 5.7 MB/s/스레드 |

- 비율 목표 45.4%는 사실상 **LZMA2 프리셋 6의 단일 스트림 결과와 같은 값**입니다.
- LZMA2 6의 단일 스레드 속도는 약 5.7 MB/s입니다. 12스레드로 완벽하게 확장해도 상한이 약 68 MB/s이고, 병렬화하려면 블록을 나눠야 해서 압축률이 다시 떨어집니다(확장자 그룹 + 약 2.4 MB 블록 시험: 약 45.6%).
- 따라서 **"80 MB/s에서 45.4% 이하"는 현재 알려진 코덱으로는 6코어 12스레드에서 동시에 달성하기 어렵습니다.** 70% 기준선(56 MB/s)도 LZMA2 6 병렬 구성의 이론 상한에 가까운 수준입니다.

### 4.2 K4: 격차는 대부분 실행파일 구성요소에서 발생

| 구성 (원본 크기) | zstd 19 | LZMA2 6 (실행파일은 +BCJ x86) | 차이 |
|---|---:|---:|---:|
| 텍스트 (28.7 MB) | 46.14% | 45.40% | 0.74pp → 0.21 MB |
| JAR (51.8 MB) | 88.21% (zstd 9: 88.51%) | 88.36% | 거의 같음 |
| 실행파일 (24.6 MB) | **33.77%** | **26.37%** | **7.4pp → 1.82 MB** |

- 혼합 셋에서 zstd가 7z보다 1.5~2pp 큰 원인의 약 85%는 exe·dll입니다. LZMA의 리터럴 문맥 모델과 BCJ 필터가 x86 코드에서 크게 앞섭니다.
- JAR(이미 압축된 데이터)은 어떤 코덱으로도 약 88%에 머뭅니다. 따라서 고레벨에 시간을 쓸 이유가 없습니다(zstd 19와 9의 차이는 0.3pp인데 시간은 7배).

### 4.3 K5 (참고): 해제는 파일시스템과 Defender 바운드

`NZ_TRACE=1`로 단계별 CPU 시간(12스레드 합)을 쟀습니다: 디코딩 0.6초, 파일 생성 5.0초, 쓰기 4.3초, 닫기 1.3초. **디코딩은 전체의 약 5%뿐**입니다. 같은 파일을 `robocopy /MT:12`로 복사하는 데 0.48~0.71초가 걸리므로, 이 장비의 파일시스템 하한은 약 0.5초입니다. 디렉터리를 미리 한 번에 만들고 큰 파일을 사전 할당하도록 바꿔 1.28초에서 약 1.05초(프로세스 내)로 줄였지만, 0.6초 목표에는 아직 멉니다.

## 5. 설계 수정안 (로드맵 게이트)

### 수정안 A: 파일 유형별 코덱 라우팅 + 유형별 솔리드 블록 병렬화 (K2·K4)

기본 모드를 "zstd 단일 스트림"에서 아래 구조로 바꿀 것을 제안합니다.

1. 계획기가 파일을 분류합니다: 텍스트·소스류 / 실행 코드(PE·ELF 매직) / 이미 압축됨(Fast·Store 등급) / 기타.
2. 유형별로 파일을 모아 **솔리드 블록(7z의 folder에 해당)**을 만들고, 블록 단위로 병렬 압축합니다. 블록 크기는 "총 입력 ÷ 스레드 수"를 기준으로 하되 최소 4 MiB로 둡니다. 같은 유형끼리 묶으므로 블록을 나눠도 압축률 손실이 작습니다.
3. 유형별 코덱: 실행 코드는 **BCJ x86 + LZMA2**, 텍스트는 LZMA2(빠른 매치파인더 hc4, 프리셋 4~6) 또는 zstd 19, 이미 압축된 데이터는 zstd 3 또는 Store.
4. 컨테이너: 표준 **7z**(folder별로 코더 체인을 따로 둘 수 있음, LZMA2·BCJ는 표준)를 우선으로 하고, `.nz`는 같은 구조를 씁니다.

추정(위 4.2의 구성요소 실측값을 조합): 혼합 셋 **62.2% 안팎**(목표 62.4% 이하). CPU 합계는 약 11.3초(텍스트 LZMA 5.0초 + 실행파일 6.0초 + JAR zstd 약 0.3초)이므로, 12스레드에서 **1.0~1.5초**를 예상합니다(목표 2.0초). 블록 분할 손실은 아직 검증하지 않았으므로 **M1 첫 주에 liblzma FFI로 프로토타입을 만들어 실측합니다.**

### 수정안 B: K2 목표 재정의 (스펙 결정 필요)

4.1의 근거에 따라 "80 MB/s에서 45.4% 이하"는 물리적 상한에 가깝습니다. 다음 중 하나로 다시 정할 것을 제안합니다.

- **B1:** "45.4% 이하에서 40 MB/s 이상"
- **B2:** "80 MB/s에서 47.0% 이하" (zstd 고레벨에 MT 튜닝을 더하고 유형 라우팅을 적용한 지점)

어느 쪽이든 수정안 A를 구현하고 실측한 뒤 확정합니다.

### 수정안 C: 해제 I/O 경로 (K5)

파일 생성과 닫기에 드는 비용을 줄입니다. 디렉터리별로 작업을 나눠 NTFS 디렉터리 잠금 경합을 줄이고, 비동기 닫기(닫기 전용 스레드 풀)를 쓰며, `FILE_FLAG_SEQUENTIAL_SCAN`을 쓰고 사전 할당을 확대합니다. **Dev Drive(ReFS, Defender 성능 모드)에서도 따로 측정**해 Defender 영향을 분리합니다. tar.zst 해제(1.4~2.0초)는 현재 단일 스레드라 zstd 디코딩과 파일 쓰기를 파이프라인으로 나누는 것이 우선입니다.

## 6. M0에서 확정·발견한 기술 사항

1. **libdeflate에는 사전(dictionary) API가 없습니다.** 그래서 pigz 방식 중 "앞 블록 32 KiB 사전"은 구현할 수 없었습니다. 대신 각 128 KiB 블록을 libdeflate로 독립 압축한 뒤, 블록 구조 스캐너(`deflate::scan_blocks`)로 마지막 블록의 BFINAL 비트를 지우고 sync-flush 표식(`00 00 FF FF`)을 붙여 하나의 표준 Deflate 스트림으로 잇습니다. 사전이 없어서 생기는 압축률 손실은 텍스트 셋에서 약 0.1pp입니다(128 KiB와 1 MiB 블록의 차이: 51.21% 대 51.12%).
2. **계획기 v1(첫 64 KiB를 LZ4로 압축해 97% 초과면 Store)은 JAR·ZIP을 잘못 분류합니다.** 앞부분은 압축된 엔트리지만 끝의 중앙 디렉터리는 압축되기 때문입니다. 혼합 셋 ZIP 압축률이 68.66%에서 71.38%로 2.7pp 나빠졌습니다. **v2**에서는 64 KiB 예산을 앞·중간·끝 3구간으로 나눠, 3구간 모두 압축 불가일 때만 Store, 2구간 이상이 압축 불가면 Fast 등급(ZIP은 libdeflate 2, tar.zst는 별도 zstd 3 프레임)으로 처리합니다. 결과: 혼합 ZIP 68.72%, 텍스트 ZIP 51.01%(v1은 51.21%).
3. **디렉터리 엔트리가 배치를 끊는 버그:** 처음 구현에서는 디렉터리가 나올 때마다 병렬 배치가 끝나 실제 병렬도가 1~4파일에 그쳤습니다. 디렉터리를 배치 안에 포함하도록 고친 뒤 텍스트 ZIP이 약 250 MB/s에서 380 MB/s(프로세스 내)로 빨라졌습니다. 배치 k+1 압축과 배치 k 쓰기도 겹쳐서 실행합니다.
4. **zstd MT의 기본 job 크기는 고레벨에서 윈도 크기의 4배(32 MiB 이상)입니다.** 그래서 28 MB 입력이 사실상 단일 스레드로 처리되었습니다. 레벨 16 이상에서는 2 MiB job과 overlap log 6을 기본으로 둡니다(레벨 19 기준 4배 빠르고, 압축률 손실 0.05pp).
5. **결정론:** ZIP은 청크 경계가 스레드 수와 무관하고, zstd MT는 워커 수가 1 이상이면 출력이 워커 수와 무관합니다(항상 MT 모드로 실행). 실데이터(혼합 셋)에서 `-t:1`, `-t:4`, `-t:12`로 만든 아카이브의 SHA-256이 같음을 zip l5·l9, tar.zst l5·l8에서 확인했습니다.
6. **ZIP 호환성:** 일부 Windows 압축 프로그램은 ZIP 이름을 CP949(UTF-8 플래그 없음)로 쓰고, 0x7075 Unicode Path 확장에 UTF-8 이름을 담습니다. 리더가 0x7075를 처리하도록 했고, 확장이 없는 레거시 이름은 CP437로 디코딩합니다.

- `cargo test --release`: 단위 테스트 17개 + 종단 테스트 7개 **모두 통과**. 종단 테스트 범위:

  - **PowerShell `Expand-Archive`**가 nz ZIP을 바이트 일치로 해제
  - 외부 콘솔 압축 프로그램의 무결성 검사·해제가 nz ZIP(l1/5/9)을 바이트 일치로 해제
  - nz가 외부 도구로 만든 ZIP을 바이트 일치로 해제
- 합성 코퍼스: 빈 파일, 1바이트 파일, 128 KiB 경계 ±1, 2 MB 텍스트, 난수(Store), JAR 유사 파일(Fast), 한글 경로, 깊은 경로, 빈 디렉터리
