# 1.0 성능 3차 (2026-11-24, 브랜치 `perf-3`)

- 기준: main `a82e644` (NextZip 1.0.0). 비교 대상은 같은 시간에 번갈아 잰 main 빌드입니다.
- 측정: 케이스마다 워밍업 1회 + 7회 측정의 중앙값, 12스레드, 같은 조건으로 2회. exe는 Defender 영향을 피하려고 스크래치 폴더로 복사해 실행했습니다.
- 부하 조건: 측정 직전 5초 샘플에서 전체 0.56~0.94코어, 단일 프로세스 최대 0.46코어(전체 3코어 미만, 1코어 이상 프로세스 없음).
- 이 문서에는 NextZip 자체의 절대 수치만 싣습니다. 상대 게이트는 같은 실행에서 비교 도구와 번갈아 재서 판정했고, 비교 도구의 수치는 저장소에 싣지 않습니다.
- 원자료: `bench/results/1.0p3/` (`nz bench` 결과, 번갈아 잰 main/perf-3 로그, K6 로그).

## 2. 변경

### 2.1 출력 파일 매핑 (`nz-sys::FileMapping`)

- `WriteFile`로 큰 출력을 쓰면 한 스레드가 모든 바이트를 시스템 캐시로 복사합니다.
  - 측정(`wrbench`): 72 MiB는 17 ms(4.5 GB/s), 2 GiB는 456~513 ms(4.1~4.6 GB/s).
- 출력 파일을 매핑하고 12스레드가 나눠 채우면 72 MiB 8.5 ms, 2 GiB 234~266 ms(7.9~9.0 GB/s)입니다.
  - 단, 한 스레드가 새 페이지를 채우면 `WriteFile`보다 느립니다(2 GiB 1스레드 703 ms). 그래서 여러 스레드가 함께 채울 때만 씁니다.
- `nz-sys`에 창(view) 단위 매핑 API를 넣었습니다. `unsafe`는 지금처럼 `nz-sys` 안에만 있습니다.
  - `FileMapping::new(file, len)`, `view(offset, len)`, `MappedView::as_mut_slice()`/`finish()`
  - Windows가 아닌 시스템에서는 `Unsupported` 오류를 내고, 호출하는 쪽이 기존 경로로 돌아갑니다.

### 2.2 K6: tar 큰 멤버 쓰기 (`tarfam`)

**원인** (1.0 최종 측정): 쓰기 스레드가 전체 시간의 약 96%를 `WriteFile`에서 보냈습니다.

**방식**

1. 8 MiB를 넘는 멤버는 출력 파일을 128 MiB 창 단위로 매핑합니다.
2. 창마다 풀 스레드들이 8 MiB 조각의 페이지를 먼저 건드려(0으로 채워진 페이지 확보) 둡니다.
3. 스트림을 읽는 스레드는 준비된 조각에 디코딩된 데이터를 바로 읽어 넣습니다. 복사는 한 번뿐입니다.
4. 다 채운 창은 보조 스레드가 해제(unmap)합니다. 동시에 매핑된 창은 최대 2개라 작업 집합이 제한됩니다.
5. 매핑이 실패하면 기존 쓰기 스레드 방식으로 씁니다.

**함께 바꾼 것**: 병렬 zstd 디코더 뒤의 `ReadAhead` 복사 단계를 뺐습니다. 디코더가 이미 자기 스레드에서 디코딩하므로 그 단계는 2.1 GB를 한 번 더 복사하기만 했습니다. 다른 코덱(gzip, xz, bzip2, lz4, 비압축)은 그대로 `ReadAhead`를 씁니다.

**시도한 방식** (큰 멤버 쓰기 시간, NZ_TRACE)

| 방식 | 시간 |
|---|---:|
| 8 MiB 버퍼로 읽고 풀이 매핑에 병렬 복사 | 738~777 ms |
| 위 + `ReadAhead` 제거 | 637~662 ms |
| 위 + 창 해제를 보조 스레드로 | 변화 거의 없음 |
| 페이지 미리 건드리기 + 매핑에 바로 읽기 (채택) | 554~611 ms |
| (참고) 매핑에 복사하지 않을 때의 읽기 바닥 | 458~514 ms |

**메모리 (K9)**: 최대 commit 579~646 MiB(main 762 MiB), 최대 작업 집합 713~717 MiB(main 586 MiB). 매핑된 파일 페이지가 작업 집합에 잡혀서 늘었지만 1 GB(954 MiB) 아래입니다. 창을 256 MiB로 두면 작업 집합이 1,009 MiB까지 올라가서 128 MiB로 줄였습니다(속도는 같음).

### 2.3 K1b: ZIP 압축 출력 매핑 (`zip::write_zip_mapped`)

**원인**: 쓰기 스레드가 압축이 끝난 뒤에도 텍스트 세트에서 7 ms, 혼합 세트에서 22~25 ms 더 돌았습니다. 아카이브 대부분을 마지막에 한 스레드가 캐시로 복사했기 때문입니다.

**방식**

1. 출력 파일을 크기 상한(입력 크기 + 헤더 여유)으로 매핑합니다. 압축 결과가 입력보다 크면 저장(stored)하므로 상한을 넘지 않습니다.
2. 파일은 지금처럼 큰 것부터 병렬로 압축합니다.
3. 앞선 항목이 모두 준비되면 입력 순서대로 위치를 정합니다. 위치를 정한 스레드가 풀의 도움을 받아 1 MiB 조각으로 병렬 복사합니다.
4. 끝에 중앙 디렉터리를 쓰고, 매핑을 해제한 뒤 실제 길이로 자릅니다.

**결정성**: 위치는 입력 순서로만 정해지므로 바이트가 기존 쓰기와 같습니다. 새 테스트 `mapped_writer_matches_streamed_writer`가 1/3/8스레드 매핑 결과와 기존 결과가 같은지 확인합니다. 실데이터에서도 md5가 같았습니다.

**적용 범위**: 입력 64 MiB~1 GiB이고 64 MiB 넘는 파일이 없을 때만 씁니다. 27 MiB 텍스트 세트에서는 매핑 쪽이 0.5~2 ms 느려서 기존 쓰기를 그대로 씁니다.

### 2.4 K5: ZIP 해제 폴더 만들기 (`nz-archive`)

`nz x`의 ZIP·ALZ·EGG 해제는 `nz-archive`를 씁니다.

- **이전**: 파일마다 `create_dir_all`을 불렀습니다(멤버마다 실패하는 `CreateDirectory` 1회).
- **처음 시도**: 해제 전에 폴더를 한 번에 병렬로 만들었습니다. 그래도 폴더 249개에 20~35 ms가 걸렸습니다. 폴더 하나에 약 1 ms의 스레드 시간입니다.
- **채택**: 각 파일의 상위 폴더를 그 폴더가 처음 필요한 멤버가 만듭니다(`OnceLock`). 그래서 폴더 생성이 다른 파일 쓰기와 겹칩니다. 목록에 있는 빈 폴더는 끝에 만듭니다. 격리 디코더 경로는 디코더가 파일을 직접 쓰므로 지금처럼 미리 다 만듭니다.
- **결과**: 25회 번갈아 측정한 중앙값입니다(예외 폴더, 저장 방식 ZIP).

| 방식 | 중앙값 |
|---|---:|
| 이전 | 0.2166 s |
| 미리 병렬 생성 | 0.2039 s |
| 필요할 때 생성 (채택) | 0.2007 s |

### 2.5 도구

- `zipcost` 예제: ZIP 레벨 5의 단일 스레드 비용을 확장자별로 나눕니다(읽기 / 플래너 / Deflate).

## 3. 프로파일 (다음 작업용)

### K1 (ZIP 텍스트, 1,211개 파일 27.38 MiB)

단일 스레드 비용(`zipcost`)은 다음과 같습니다.

| 항목 | 비용 |
|---|---:|
| 읽기 (파일 열기·읽기·닫기) | 57~74 ms (파일당 약 50~60 µs) |
| 플래너 | 10 ms |
| Deflate | 131~149 ms |

- Deflate의 대부분은 `.sla` 137개(이미 zlib 스트림, 12.25 MB) 77 ms와 `.sinc` 200개(11.36 MB, libdeflate L6) 47 ms입니다.
- 12스레드 압축 단계는 35~43 ms로, 이미 단일 스레드 비용의 약 6.5~7배를 내고 있습니다. 물리 코어가 6개라 이 이상은 CPU를 줄여야 합니다.
- **압축률 예산**: 14,712,316 B까지 남은 여유는 75 KB입니다. 레벨을 바꾸면 이 여유를 넘습니다.

| 설정 | 크기 변화 | 단일 스레드 CPU |
|---|---:|---:|
| `.sinc` L6 → L5 | +46 KB | −10 ms |
| `.sinc` L6 → L4 | +111 KB | −15 ms |
| 압축된 데이터 L2 → L1 | +85 KB | −13 ms |
| 압축된 데이터 L2 → 허프만+탐욕 LZ (자체 인코더) | +205 KB | −40 ms |

- 프로세스 시작·종료와 폴더 탐색(5~6 ms)을 빼면 압축에 쓸 수 있는 시간이 작습니다.
- 탐색과 압축을 겹치는 방식(탐색 중 발견한 파일부터 압축)은 이득이 3 ms 안팎으로 예상돼 하지 않았습니다.

- 단일 스레드 비용은 다음과 같습니다.

| 항목 | 비용 |
|---|---:|

| 플래너 | 19 ms |

### K5 엔진

- 폴더 생성이 폴더당 약 1 ms(스레드 시간), 파일 하나의 생성·쓰기·닫기가 약 1.4 ms(스레드 시간)입니다. NTFS가 바닥입니다.

- 스레드 수 24는 12와 차이가 잡음 범위였습니다.

### K6
