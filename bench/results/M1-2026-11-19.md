# M1 실측 결과 (수정안 A: 유형별 코덱 라우팅) — 2026-11-19 ~ 11-20

M0 게이트 문서 5장의 **수정안 A**(파일 유형별 코덱 라우팅 + 유형별 솔리드 블록 병렬화 + 표준 7z 컨테이너)를 구현하고, 같은 데이터로 K2·K4를 다시 측정했습니다. 이어서 7z 안의 ZIP·JAR 컨테이너 zstd 라우팅, ZIP 쓰기 파이프라인, ZIP 컨테이너용 자체 Deflate 인코더, 병렬 디렉터리 탐색을 더했습니다.

## 1. 요약

- 데이터셋: 텍스트 `text_processors`(1,211개 파일, 27.38 MiB), 혼합 전체(1,444개 파일, 100.25 MiB). 장비: Ryzen 5 9600X(6코어 12스레드), Defender 실시간 보호 켜짐.
- 이 장비는 상주 프로그램 때문에 외부 부하가 1~3.6코어 아래로 내려가지 않았습니다. 절대 시간은 부하에 따라 20~30% 흔들립니다.

| 항목 | 3차 (11-19, 부하 2.25코어) | **6차 (11-20, zstd 컨테이너 + ZIP 개선)** | 8차 (11-20, ZIP만) |
|---|---|---|---|
| 7z `-l:6` 텍스트 | 45.16%, 1.062초 (25.8 MB/s) | **45.16%, 0.887초 (30.9 MB/s)** | — |
| 7z `-l:6` 혼합 | 62.37%, 4.32초 | **62.20%, 3.02초** | — |
| ZIP `-l:5` 텍스트 | 51.01%, 0.070초 (394 MB/s) | 50.96%, 0.064초 | **50.98%, 0.049초 (약 560 MB/s)** |
| ZIP `-l:5` 혼합 | 68.72%, 0.306초 | 68.65%, 0.185초 | **68.87%, 0.137초 (약 730 MB/s)** |
| 7z 해제 혼합 | 1.29초 | **0.90초** | — |
| ZIP 해제 혼합 | 0.98초 | **0.89초** | — |

**결론**

- 유형별 라우팅으로 M0의 zstd 단일 경로가 닿지 못했던 압축률(텍스트 45.2%, 혼합 62.2%)에 도달했습니다.
- 7z 속도의 바닥은 LZMA2 bt4의 단일 스레드 속도(이 장비에서 텍스트 3.4~5.3 MB/s, 4.2장)입니다. 6코어에서 1→12스레드 확장은 4.8배였습니다.
- ZIP은 자체 컨테이너 Deflate 인코더와 병렬 탐색으로 텍스트 0.049초, 혼합 0.137초까지 줄었습니다.
- ZIP 해제는 Defender 실시간 검사가 바닥값을 정합니다(4.6장).
- **재측정 중 발견한 버그(수정함):** 체인 세그먼트가 딕셔너리를 프리셋 크기(preset 9 = 64 MiB)로 잡아, 혼합 셋 `-l:9`에서 bt4 인코더 12개가 메모리 할당에 실패했습니다(`liblzma error 5`). 필요한 크기는 "프리로드 + 세그먼트"뿐이라 그 크기로 줄였고, 압축 데이터는 같고 헤더의 딕셔너리 속성 값만 작아집니다. 회귀 테스트를 추가했습니다.

6차부터 바뀐 점(4.7장):

- **ZIP·JAR 컨테이너**(첫 4바이트 `PK\x03\x04`, 새 클래스 `zip`)는 zstd(7-Zip ZS 메서드 `04 F7 11 01`)로 한 폴더에 압축합니다.
  - zstd 레벨은 7z 레벨 1~2 → 3, 3~5 → 9, 6~7 → 12, 8~9 → 19입니다.
  - long window는 128 MiB이고, 2 MiB 작업 단위로 멀티스레드 압축합니다.
  - `-zipc:lzma2`로 예전 LZMA2 경로를 쓸 수 있습니다.
- other·Fast 등급 세그먼트:
  - 레벨 5~8은 1 MiB 세그먼트 + 1 MiB 체인 프리로드입니다(`-oseg`, `-opre`).
  - 레벨 9는 4 MiB 세그먼트 + 1 MiB 프리로드입니다.
  - 레벨 0~4는 예전과 같이 2 MiB 독립 세그먼트입니다.
- 폴더는 큰 것부터 병렬 압축을 시작하고, 결과는 원래 폴더 순서로 씁니다. 출력 바이트는 바뀌지 않습니다.

## 4. 분석

### 4.1 유형별 라우팅의 효과와 발견 사항

1. **실행 코드는 한 폴더에 모아야 합니다.** 실행 파일 19 MB를 3개 블록으로 나누면 BCJ+LZMA2가 31.98%, 한 블록이면 26.46%입니다(5.5pp). 공통 런타임·정적 라이브러리가 파일 사이에서 반복되기 때문입니다. 그래서 실행 코드는 64 MiB 폴더 하나에 **체인 세그먼트**(4 MiB, 4 MiB 프리로드: 26.65%)로 병렬화합니다. BCJ 효과: 같은 조건에서 BCJ 없이 27.78%, BCJ로 26.46%.
2. **"압축 불가" 판정 파일도 파일 간 중복이 있습니다.** LZ4 샘플링에서 Store로 분류된 바이너리 데이터 파일(zlib 압축본)들은 변형끼리 같은 바이트열을 공유합니다. 레벨 6 이상에서 Fast·Store 등급을 끄고 LZMA2(lc0 pb0)로 넣으면 텍스트 셋 레벨 9 기준 45.38% → 45.03%입니다.
3. **이미 압축된 데이터에는 lc=0, pb=0이 유리합니다**(텍스트 셋 45.57% → 45.50%). 텍스트 자체에는 pb=0이 소폭 유리합니다(→45.47%).
4. **JAR에서는 체인 세그먼트 이득이 거의 없습니다**(86.45% → 86.27%, 시간 1.4배).
5. **Fast 등급에 Deflate는 부적합합니다.** JAR류에서 Deflate는 92.93%, LZMA2는 90.8% 이하라 기본값을 LZMA2로 바꿨습니다(`-fast:deflate`로 선택 가능).
6. **헤더 압축은 필수입니다.** 1,444개 파일의 평문 헤더는 약 182 KB(혼합 셋의 0.18pp)라 LZMA2로 압축합니다.

### 4.2 7z 텍스트 속도의 한계

- LZMA2 bt4 프리셋 6의 단일 스레드 속도는 이 장비에서 텍스트 셋 기준 **3.4~5.3 MB/s**입니다.
- 40 MB/s를 내려면 단일 스레드 대비 12배 확장이 필요한데, 물리 코어가 6개라 불가능합니다. 1→12스레드 확장은 4.8~5.6배였습니다.
- 45.4%를 지키면서 더 빠른 설정은 없었습니다. hc4로 바꾸면 2배 빨라지지만 46.4% 이상으로 떨어집니다(`-l:3` 46.48%, 48.6 MB/s).

### 4.3 M0 추정과의 비교

| 항목 | M0 추정 | M1 실측 (`-l:6`) |
|---|---|---|
| 압축률 | 62.2% 안팎 | **62.37%** → 6차 62.20% |
| 시간 (12스레드) | 1.0~1.5초 | **4.32초 (3차)** → 6차 3.02초 |

- 압축률 추정은 거의 맞았습니다.
- 시간 추정이 틀린 이유: (1) 단일 스레드 LZMA2 속도를 5.7 MB/s로 잡았지만 실제는 3.4~5.3 MB/s입니다. (2) JAR 51.8 MB를 LZMA2로 처리하는 비용을 과소평가했습니다(6차에서 zstd 라우팅으로 해결). (3) 6코어 12스레드에서 LZMA 확장은 약 5~6배에 그칩니다.

### 4.4 해제

7z 해제는 folder 단위 병렬입니다. 레벨 9의 혼합 해제가 느린 것은 64 MiB 체인 폴더가 단일 스트림이라 병렬 해제가 안 되기 때문입니다.

### 4.5 인코더 최적화 시험 (2026-11-20)

텍스트 셋을 이어 붙인 28.71 MB를 2 MiB 독립 세그먼트로 나눠 **단일 스레드**로 인코딩했습니다(번갈아 3라운드 중앙값, 상대 비교만).

| 인코더 | 설정 | 압축률 | 시간 (초) | MB/s |
|---|---|---:|---:|---:|
| xz liblzma 5.8 (현재) | p6 bt4 nice128 pb0 | 45.480% | 6.093 | 4.7 |
| 7-Zip LZMA SDK 25.01 `Lzma2Enc` | l6 bt4 fb128 pb0 | 45.475% | 5.832 | 4.9 |
| xz | p3 hc4 nice32 | 46.424% | 3.008 | 9.5 |
| 7-Zip SDK | l3 hc4 fb32 | 46.501% | 2.085 | 13.8 |

- 7-Zip SDK로 바꿔도 bt4 설정은 4~10%만 빨라집니다. MSVC 플래그(`/Ob3 /arch:AVX2 /GS- /Gw`)는 효과가 없었습니다.
- 재현: `cargo run --release -p nz-core --example lzbench -- <dir> 1 3`.

### 4.6 zstd 컨테이너 라우팅과 ZIP 파이프라인 (5·6차)

1. **7z: ZIP·JAR 컨테이너를 zstd로 압축합니다.** 이런 파일은 zstd(레벨 9~15 + long window)가 LZMA2와 압축률이 같거나 더 좋고 약 10배 빠릅니다(`examples/classbench.rs`). 바이너리 데이터 파일은 반대로 LZMA2가 약 5%p 좋아서 LZMA2에 남겼습니다. zstd 메서드는 7-Zip ZS 계열 리더가 읽습니다.
2. **7z: other 데이터를 1 MiB 세그먼트 + 1 MiB 프리로드로 압축합니다.** 텍스트 `-l:6`이 1.00초에서 0.79초로 줄었고, 크기는 3.5 KB(+0.01%p) 늘었습니다.
3. **ZIP 쓰기 파이프라인:** 압축되는 대로 입력 순서대로 쓰는 전용 쓰기 스레드, 작은 파일은 청크로 나누지 않음, 큰 파일부터 압축 시작, ZIP 안의 ZIP·JAR은 Fast 등급. 혼합 zip:5가 0.258초에서 0.185초로 줄었습니다.

**ZIP 해제 분석:** 12스레드 CPU 시간 합계는 디코드 0.5~0.7초, 파일 생성 4.5~5.4초, 쓰기 3.2~4.1초, 닫기 1.0~1.3초였지만, 프로세스가 실제로 쓴 CPU는 약 1초뿐이었습니다. 같은 파일 1,444개를 내용 없이 만들면 0.23초, 내용을 쓰면 0.85~0.95초였습니다. Defender 실시간 검사가 바닥값입니다. 실시간 검사를 피해 가는 방식은 쓰지 않습니다.

### 4.7 ZIP 컨테이너용 자체 Deflate 인코더 (7차)

혼합 셋 ZIP 압축 CPU의 절반가량은 이미 Deflate로 압축된 JAR·ZIP 데이터에서 매치를 찾는 시간이었습니다. 그래서 ZIP 계열 파일 전용 표준 raw Deflate 인코더(`crates/nz-core/src/hdeflate.rs`)를 만들었습니다. 출력은 일반 Deflate 스트림입니다.

- **구간 분류** (`deflate::container_runs`): 로컬 헤더와 1 KiB 미만 멤버는 해시 기반 탐욕 LZ, 1 KiB 이상의 압축 멤버 데이터는 리터럴과 블록별 동적 Huffman만, 4 KiB 이상의 저장 멤버와 중앙 디렉터리는 libdeflate(레벨 6).
- **크기를 모르는 멤버:** 데이터 디스크립터를 쓰는 JAR는 중앙 디렉터리에서 크기를 읽습니다.
- **속도 최적화:** 리터럴 구간 토큰 묶기, 4중 히스토그램, 코드 두 개 동시 출력, 8바이트 단위 일치 비교, 적응형 탐색 간격, 스레드별 해시 테이블 재사용.
- **효과 (1스레드, JAR 50 MB):** libdeflate 레벨 1은 405 ms에 46,761,511 B, 자체 인코더는 약 160 ms에 46,903,589 B.
- **혼합 셋 전체:** 내부 시간 139 → 121 ms. 크기 72,391,199 B(68.87%).

### 4.8 실행 파일 경로와 병렬 탐색 (8차)

- 실행 파일 24 MB의 1스레드 libdeflate CPU는 L6 기준 약 196 ms입니다. 64 KB 블록 단위로 압축 불가 구간이 없어(0.9 이상 블록 0.4%) 리소스 분리로 얻을 것이 없고, L4는 크기 +171 KB입니다. 실행 파일 경로는 libdeflate L6이 최선입니다.
- **병렬 탐색** (`walk.rs`): `walkdir` 순차 탐색을 rayon 병렬 재귀로 바꿨습니다(형제 이름 정렬·깊이 우선 순서 유지). 혼합 셋 탐색 시간이 11 ms에서 약 2.5 ms로 줄었고, 출력은 `-t:1`과 `-t:12`에서 같습니다.
- 8차: 텍스트 0.049초(50.98%), 혼합 0.137초(68.87%).

### 4.9 빠른 프리셋 시험 (9~11차)

텍스트가 아닌 파일의 libdeflate 레벨을 따로 정하는 `-dlb:N`을 추가했습니다(기본 동작은 그대로).

| 혼합 설정 | 시간 (11차) | 압축률 |
|---|---:|---:|
| `zip:5` (기본) | 0.141초 | 68.87% |
| `dlb=2` | 0.134초 | 69.10% |
| `dlb=1` | 0.126초 | 69.53% |
| `dl=1` | 0.116초 | 70.12% |

텍스트 셋은 `zip:5` 0.054초(50.98%), `dlb=1` 0.051초(51.15%). 기본값은 바꾸지 않았고, `-dlb:1`은 "빠른 우선" 프리셋 후보로 남겨 둡니다.

## 5. 설계 결정과 근거

- **블록 크기 공식의 분모는 `-t`가 아니라 고정 상수 12(`PLAN_SPLIT`)입니다.** "출력은 스레드 수와 무관하게 결정론적" 요구 때문입니다. `-block:KiB`로 바꿀 수 있습니다.
- **`unsafe`는 `crates/nz-xz` 한 곳에만 둡니다.** safe `liblzma` crate가 preset dictionary를 노출하지 않아 liblzma-sys 직접 호출이 필요했습니다. `nz-core`·`nz-cli`는 `unsafe_code = forbid`를 유지합니다.
- **7z에서 Fast 등급 기본 코덱은 LZMA2**입니다(4.1장 5항).
- **7z 안의 ZIP·JAR 컨테이너는 zstd**입니다(6차부터). 7-Zip 본가 표준 메서드는 아니지만 7-Zip ZS 계열 리더가 읽습니다. `-zipc:lzma2`로 끌 수 있습니다.

## 6. 검증 현황

- `cargo test --release`: 단위 테스트 26개 + 종단 테스트 9개 **모두 통과**.
  - 새 단위 테스트: BCJ x86이 liblzma와 바이트 일치·왕복, LZMA2 독립·체인 세그먼트를 liblzma가 한 스트림으로 해제(딕셔너리 크기 회귀 포함), 7z NUMBER 인코딩, 블록 분할 균형, FILETIME 왕복, 유형 분류
  - 새 종단 테스트: 7z c→x 왕복(l0/1/5/9), **스레드 1/3/12 결정론(7z l5·l9)**, 외부 7z 리더와의 상호 해제(`NZ_REF_ARCHIVER`)
  - 6차에서 합성 코퍼스에 5 MB ZIP 컨테이너를 추가해 zstd 폴더 왕복과 결정론을 함께 검사합니다.
  - 7z 호환 테스트를 **실데이터(`NZ_COMPAT_DATA`, 1,444개 파일)로도 실행해 통과**
