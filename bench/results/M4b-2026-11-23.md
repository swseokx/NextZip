# M4b 보고서 — ADS · 압축률 격차 · 퍼즈 처리량 (2026-11-23)

브랜치 `m4-rest` (main 216b570에서 분기). push와 main 병합은 하지 않았습니다.
"이전"은 216b570을 같은 PC에서 빌드한 `nz.exe`, "이후"는 이 브랜치입니다.

## 1. NTFS 대체 데이터 스트림(ADS)

- **수집:** Windows에서 파일마다 `FindFirstStreamW`로 이름 있는 `$DATA` 스트림을
  찾아(병렬), 파일 내용 바로 뒤에 이름 순으로 청크를 추가합니다. 인덱스의 기존
  `streams` 필드(kind 0)를 그대로 쓰므로 **인덱스 인코딩은 바뀌지 않았습니다.**
  스트림도 중복 제거됩니다(파일과 같은 내용의 스트림은 청크를 공유).
- **복원:** `<파일>:<이름>`으로 내용 다음, 수정 시각·읽기 전용 속성 설정 전에
  씁니다. FAT처럼 스트림이 없는 곳에서는 파일은 두고 `stream_errors`로 보고합니다.
  데이터 손상이면 기존처럼 항목 실패 → 복구 기록 적용 후 재시도.
- **보안:** kind 0 이름은 1–255 UTF-16 단위, `:` `/` `\` `<>"|?*`·제어 문자 금지.
  어기면 경로와 같은 정책으로 **아카이브 전체를 거부**합니다(`x:$DATA`,
  `$INDEX_ALLOCATION` 같은 스트림 형식 지정 차단). MotW 전파(nz-archive)는 추출 뒤에
  실행되므로 인터넷 영역 아카이브에서는 저장된 `Zone.Identifier`가 덮어써집니다.
- **xattr(kind 1):** Windows에서 의미가 없어 쓰지 않고, 추출기는 무시합니다(예약).
  디렉터리·링크의 스트림도 저장하지 않습니다.
- **옵션:** 기본 켜짐. `nz c`/`nz backup`의 `-noads`로 끕니다.
  API는 `WriteOptions::keep_streams`. Win32 호출은 unsafe가 허용된 `nz-sys`
  (`alternate_streams`, `Win32_Storage_FileSystem` 기능 추가)에 두었습니다.
- **테스트:** `alternate_data_streams_round_trip`(빈 스트림·700 KB 스트림·중복
  제거·`keep_streams: false`), `unsafe_stream_names_are_rejected`.

## 2. 압축률 격차

### 2.1 원인 (분석 실험, 단일 스레드)

| 원인 | 크기 영향 |
|---|---|
| 복구 기록 3% (기본값) | 약 2.3%p — 사용자 결정으로 **유지** |
| x86 코드에 BCJ 없음·작은 창 | mixed의 exe/dll 18.5 MB: zstd6 7.6 MB → BCJ+8 MiB 블록+zstd7 6.5 MB |
| 이미 압축된 데이터(.sla=zlib 등)에 zstd | text의 8 MB: zstd 7.64 MB, LZMA2 p1 7.21 MB(CPU 약 8배) |
| 블록 단위 LZ4 표본(블록당 64 KB)의 "저장" 판정 | 16 MiB 블록이 jar 데이터째 통째로 저장되는 경우 발생(레벨 8에서 확인) |
| zstd 자체의 엔트로피 부호화 한계 | 텍스트에서 LZMA2보다 1–2%p 큼. zstd 19도 LZMA2 p6보다 크고 5배 느림 |

### 2.2 바꾼 것

사용자 결정: BCJ는 v1.0에 바로 추가, 압축 데이터용 LZMA2는 레벨 6 이상에만, 복구 기록 3% 유지.

- **블록 필터 (포맷):** 블록 헤더 바이트 6(예약)을 필터 id로 정의. 0 없음, 1 x86 BCJ
  (liblzma x86 필터, 시작 오프셋 0, 블록 전체). AEAD의 AAD(0..48)에 포함됩니다.
  사양 §5.1, §6, §15(이력)에 기록. 테스트 벡터는 바이트 6이 0이라 그대로입니다.
- **클래스별 블록:** 파일마다 플래너로 분류(이미 있는 `nz_core::planner`, 파일당 표본
  최대 3개)해 열린 블록 최대 4개(일반·코드·압축됨·저장)로 나눕니다. 청크의 블록
  번호는 블록을 봉인할 때 매기므로 스레드 수와 무관하게 결정적입니다.
  - 코드(exe/dll/ELF x86): BCJ + 8 MiB 블록(레벨 2–6), 7–9는 기존 블록 크기.
  - 압축됨+저장 클래스: 레벨 6–8에서 LZMA2 p1, lc0 pb0, 1 MiB 독립 세그먼트.
  - 저장 클래스: 레벨 1–5는 그대로 저장, 9는 일반(LZMA2 p9) 블록.
  - 일반 블록은 더 이상 블록 단위 표본으로 저장 판정을 하지 않습니다
    (압축 결과가 크면 저장하는 규칙만 남음).
- **zstd:** 레벨 5를 zstd 6 → 7, 창을 `next_power_of_two(블록)`(최대 2^27)로.

### 2.4 속도

최종 실행 중 PC 부하가 높았습니다(게임 프로세스·다른 세션 빌드, 측정 시 부하 38–96%).
그래서 압축 시간은 이전/이후를 번갈아 7회씩 실행한 중앙값(`M4b/paired-compress.txt`)으로 봅니다.

| 케이스 | 이전 | 이후 | 배율 |
|---|---:|---:|---:|
| text nz:5 | 0.283 s | 0.295 s | 1.04 |
| mixed nz:5 | 0.726 s | 0.882 s | 1.22 |
| text nz:6 | 0.330 s | 0.757 s | 2.29 |
| mixed nz:6 | 0.890 s | 1.622 s | 1.82 |

- nz:5는 거의 그대로(코드 블록을 16 MiB로 하면 mixed −0.1%p 더 줄지만 1.35배라 8 MiB 채택).
- nz:6은 LZMA2 때문에 약 2배(합의된 트레이드오프). 같은 실행의 7z:5(text 1.76 s,
  mixed 3.39 s)보다는 여전히 빠릅니다.
- 추출: 같은 위치의 실행 파일끼리 비교하면 차이 없음. **주의:** 프로젝트 폴더의
  `target\release\nz.exe`는 Temp 폴더의 같은 바이너리보다 추출이 약 1.5–2배 느렸습니다
  (Defender 처리 차이로 추정, 7z 케이스까지 동일). 그래서 두 바이너리 모두 scratch
  폴더에서 실행해 측정했습니다. 이전 보고서들의 추출 시간 비교에도 영향이 있었을 수 있습니다.

원본: `bench/results/M4b/{text,mixed}-{before,after}.{md,json,log}`, `load-*.txt`.

## 3. 퍼즈 처리량

원인은 KDF가 아니라 **Rayon 전역 풀(12스레드)을 입력마다 깨우는 비용**이었습니다
(ASAN에서 특히 큼). 진입점(`nz_nzf::fuzzing`)이 이제 전용 1스레드 풀에서 실행합니다.
추가로 Argon2 마스터 키를 (비밀번호, salt, 파라미터)로 캐시합니다(퍼즈 진입점에서만
켜짐, 최대 64개). 비밀번호를 쓰는 KDF 한도는 m≤1024→256 KiB로 낮췄습니다(씨앗은 64 KiB).

cargo-fuzz(nightly, ASAN), 각 60초, 같은 코퍼스 사본(`nz-corpus\fuzz-nz\corpus`), `-seed=1`:

| 타깃 | 이전 exec/s | 이후 exec/s | 배율 | 실행 수 (이전 → 이후) |
|---|---:|---:|---:|---:|
| nz_read | 92 | **1953** | 21× | 5,613 → 119,136 |
| nz_recovery | 22 | **1054** | 48× | 1,395 → 64,338 |

- 충돌 없음(artifacts 비어 있음).
- `cov` 수치는 이후가 약 230 낮습니다(3966 → 3731). 줄어든 부분은 Rayon의 다중 스레드
  스케줄러(작업 훔치기·슬립) 경로로, 제품 코드가 아닙니다. 60초 동안 새로 늘어난
  커버리지는 이후가 더 큽니다(+17 대 +9).
- 계측 없는 단일 스레드 리플레이 도구: `cargo run --release -p nz-nzf --example fuzz_perf -- <corpus> [read|recovery]`
  (기존 코퍼스: read 약 14,000, recovery 약 7,400 exec/s).
- Windows에서 실행하려면 VS BuildTools의 `bin\Hostx64\x64`(clang_rt.asan_dynamic)를 PATH에 넣어야 합니다.
- 로그: `bench/results/M4b/fuzz-*.log`. 외부 제출 없음.

## 5. 호환성과 남은 것

- 오늘 main(216b570) 이전 빌드의 리더는 필터 바이트가 0이 아닌 블록(코드 블록)을
  거부합니다. .nz를 쓰는 릴리스가 없어 v1.0에 넣었습니다(사양 §15 이력).
- CLI 도움말: `-noads` 추가. GUI는 기본값(ADS 저장)을 따릅니다.
- 남은 격차: text nz:5(3.7%p)는 zstd로는 줄이기 어렵습니다. 더 줄이려면 nz:5에도
  LZMA2(속도 1.5–2배)나 기본 rr 축소가 필요합니다.
- 추출된 ADS 내용이 AMSI 검사에 포함되는지는 확인하지 않았습니다(nz-archive 검사는 파일 단위).
