## 2. 구현 내용

### 2.1 프로세서 그룹

| 항목 | 내용 |
|---|---|
| `nz-sys` | 새 크레이트. `windows-sys` 0.61로 `GetActiveProcessorCount(ALL_PROCESSOR_GROUPS)`, `GetLogicalProcessorInformationEx(RelationGroup)`(그룹별 활성 마스크), `SetThreadGroupAffinity`, `MultiByteToWideChar(CP_ACP)`를 부릅니다. `nz-xz`와 함께 `unsafe`가 있는 유일한 크레이트이고, `nz-core`·`nz-cli`는 계속 `unsafe_code = forbid`. 비 Windows에서는 그룹 1개, 바인딩은 아무 일도 하지 않음 |
| 논리 CPU 수 | `default_threads()`(공용 API 시그니처 그대로)가 `available_parallelism`(=`GetSystemInfo`, 그룹 하나만 봄) 대신 전체 그룹 합을 돌려줌 |
| 배분 | `cpu::assign_groups(sizes, threads)`: 순수 함수. 그룹 크기에 비례해 최대 잔여법으로 나누고(동점은 낮은 그룹), 평활 가중 라운드로빈 순서로 배치해 앞쪽 워커도 여러 그룹에 퍼짐. `threads ≤ 전체 CPU`이면 어떤 그룹도 CPU 수보다 많이 받지 않음 |
| 바인딩 | `cpu::pool()`: 그룹이 2개 이상이면 Rayon `start_handler`에서 워커 i를 배정된 그룹의 활성 마스크로 `SetThreadGroupAffinity`. 그룹 1개면 바인딩하지 않아 기존 동작과 같음. `NZ_TRACE=1`이면 그룹별 워커 수를 출력 |
| 결정론 | 배치는 바이트에 영향이 없음. 모든 작성기가 입력 크기로만 작업을 나누기 때문(기존 결정론 테스트 + 새 tar 결정론 테스트 통과) |

가상 토폴로지 단위 테스트(`cpu::tests`): 2그룹×64(128·65·9 스레드), 4그룹×48 + 20(불균등, 1~300 스레드 전부에서 각 그룹 몫이 정확한 비례값과 1 미만 차이·초과 배정 없음), 빈 그룹·크기 0 그룹, 같은 입력 같은 결과.

### 2.2 tar 계열

| 항목 | 내용 |
|---|---|
| tar 층 | POSIX ustar 헤더를 직접 씀. 이름이 ustar에 안 맞거나(100바이트 초과이고 prefix 155로도 못 나눔) ASCII가 아니면 PAX `x` 헤더의 `path=`(UTF-8)를 붙임 → Windows tar.exe(libarchive)도 한글이 깨지지 않음. 링크 대상도 같은 규칙으로 `linkpath=`. 8 GiB 넘는 크기는 PAX `size=`. uid/gid 0, 사용자 이름 없음 → 입력만으로 바이트가 정해짐. 10 KiB 레코드 단위로 패딩(GNU tar·bsdtar와 같음) |
| 입력 열거 | `walk::collect_items(sources, links)`(새 함수): 심볼릭 링크를 따라가지 않고 링크 항목으로 돌려줌. 기존 `walk::collect`는 그대로(내부에서 새 함수 사용) |
| 작은 파일 미리 읽기 | 1 MiB 이하 파일을 32 MiB 창 단위로 Rayon에서 병렬로 읽은 뒤 tar 스트림에 순서대로 씀 |
| gzip | 1 MiB 청크를 libdeflate로 병렬 압축하고 pigz 방식으로 이어 붙인 **한 멤버**(기존 `deflate::deflate_chunk`). 레벨 맵은 ZIP과 같음. 헤더 MTIME=0 |
| bzip2 | 3.6 MB(900 kB 블록 4개) 청크마다 독립 bzip2 스트림(pbzip2 방식), `bzip2` 크레이트(libbz2-rs, 순수 Rust) |
| lz4 | 한 프레임, 독립 블록 4 MiB, 블록마다 병렬 압축(l5 = HC 6), 콘텐츠 체크섬(xxh32) |
| xz | liblzma MT 인코더(`parallel` 기능 켬). 블록 크기 = `총 입력 ÷ PLAN_SPLIT(12)`를 [1 MiB, 사전×3]로 제한 → 스레드 수와 무관 |
| zstd | 기존 `tarzst`(zstd MT + 계획기 fast 프레임)를 새 tar 층으로 옮김. 공용 함수 `write_tar_zst`/`extract_tar_zst` 시그니처는 유지 |
| 파이프라인 | 청크 코덱은 배치 단위로 Rayon에 넘기고 호출 스레드는 다음 파일을 계속 읽음(이중 버퍼, 메모리 상한 배치 2개). 워커가 1개여도 교착하지 않도록 기다리는 동안 `rayon::yield_now`로 대기 작업을 직접 실행 |
| 해제 | 첫 바이트로 형식 판별(gzip·xz·bzip2·lz4·zstd·평문 tar). 디코딩은 별도 스레드(1 MiB 선읽기), 8 MiB 이하 파일 쓰기는 Rayon 워커로 넘김(대기 바이트 256 MiB 상한). xz는 MT 디코더, gzip은 다중 멤버, bzip2는 다중 스트림, lz4는 연속 프레임 지원 |
| 외부 tar 호환 | GNU `././@LongLink`(GNU 매직 없이 쓰는 도구가 있음 → `tar` 크레이트가 적용하지 않아 직접 처리), PAX, `./` 루트 항목, UTF-8이 아닌 이름은 시스템 ANSI 코드페이지(CP949)로 해석 |
| 링크 쓰기 | 링크는 tar 스트림 끝에 둠(해제 시 대상이 먼저 존재). 폴더 링크에는 PAX `LIBARCHIVE.symlinktype=dir`을 붙임: Windows tar.exe(libarchive)가 대상이 아직 없을 때도 폴더 링크로 만듦. GNU tar는 이 키에 경고 한 줄만 내고 정상 처리(bsdtar 자체 아카이브와 같음) |
| 링크 해제 | 모든 파일을 쓴 뒤 마지막에 만듦. 대상이 폴더면 폴더 링크(`symlink_dir`). 심볼릭 링크 대상이 절대 경로이거나 출력 폴더 밖이면 건너뜀(경고). 권한이 없어 링크를 못 만들면 대상 파일을 복사(경고). 하드 링크는 `hard_link`, 실패 시 복사 |
| CLI | `-fmt:tar|tar.gz|tgz|tar.xz|txz|tar.bz2|tbz2|tar.lz4|tar.zst`, 출력 확장자로 자동 판별, `nz x`가 형식 자동 판별·기본 출력 폴더에서 확장자 제거 |
| 의존성 추가 | `windows-sys`(nz-sys), `flate2`(zlib-rs 백엔드, 해제용), `bzip2`, `xxhash-rust`(xxh32), `liblzma`의 `parallel` 기능 |

### 3.3 해설

- **tgz l5**는 텍스트 260 MB/s · 혼합 312 MB/s로 압축하고, 압축률은 49.79% / 68.14%입니다.
- **tgz l9**는 ZIP과 같은 레벨 맵(l9 = libdeflate 12)을 써서 텍스트 24 MB/s로 느린 대신 압축률이 가장 좋습니다(49.25%). 같은 압축률을 더 빨리 내는 레벨 맵 조정은 후속 과제입니다.
- tar.xz:5는 7z 경로의 유형별 라우팅·BCJ가 없어 7z보다 압축률이 0.5~0.7 pp 나쁩니다.
- **tar.bz2 해제가 느립니다**(혼합 7.5초). 디코더가 단일 스레드이기 때문인데, nz가 만든 bz2는 3.6 MB 독립 스트림이라 병렬 해제가 가능합니다(후속 과제).
- tar l5 해제는 압축 없이 파일 1211개를 쓰는 시간이라 파일 시스템·Defender가 지배합니다.

참고 사항

- 일부 Windows 압축 프로그램은 압축할 때 링크를 따라가 대상 내용을 저장합니다. nz는 그 결과를 일반 파일·폴더로 풉니다.
- 일부 도구는 전체 경로가 MAX_PATH(260자)를 넘으면 해제에 실패하므로 테스트 데이터는 이 한도 안에 둡니다.
- 이름을 CP949 원시 바이트로 저장하거나 100바이트를 넘는 이름을 GNU 매직 없는 `L` 헤더로 쓰는 tar도 nz는 둘 다 읽습니다.

## 5. 검증하지 못한 것

- **다중 프로세서 그룹 실기**: 이 장비는 12 논리 CPU·단일 그룹입니다. `GetLogicalProcessorInformationEx` 파싱과 `SetThreadGroupAffinity` 호출은 단일 그룹(그룹 0)에서만 실행해 봤고, 64개 초과 장비에서 워커가 실제로 여러 그룹에 퍼지는지는 확인하지 못했습니다.
- **코덱 내부 스레드는 바인딩하지 않습니다**: zstd MT·liblzma MT가 직접 만드는 스레드는 Rayon 풀 밖이라 그룹 지정이 없습니다. Windows 11/Server 2022부터는 OS가 새 스레드를 모든 그룹에 배치하지만, Windows 10/Server 2019에서는 tar.zst·tar.xz·7z의 zstd 경로가 주 그룹(최대 64)에 머뭅니다. Rayon 경로(ZIP, 7z LZMA2 세그먼트, tar.gz·bz2·lz4)는 그룹을 넘어갑니다.
- ~~심볼릭 링크 종단 테스트~~: 처음 측정 때는 링크 생성 권한이 없었으나, 사용자가 개발자 모드를 켠 뒤 종단 검증을 마쳤습니다(4장). 이 과정에서 `tar.exe`가 폴더 링크를 파일 링크로 만드는 문제를 찾아 고쳤습니다(2.2 링크 쓰기). 권한이 없을 때의 복사 대체는 단위 테스트로만 확인했습니다.
- tar.lz4는 Windows tar.exe에 내장 lz4가 없어 tar.exe와의 상호 검증이 없습니다(nz 단위 테스트의 다중 프레임 해제로 검증).
- 외부 CPU 부하는 이번 측정에서 따로 기록하지 않았습니다.
