## 2. 측정 환경과 배경 부하

- **배경 부하** (`1.0/load.log`, 측정 직전 5초 샘플)
  - 사용 중인 코어: 합계 약 1.3~2.0
  - 주요 프로세스: chrome 0.5~1.05, AMDRSServ 0.3~0.5, Wallpaper Engine 0.3, 작업 관리자·설정 앱 0.1씩
- **대기 조건**
  - 처음에는 1코어 미만으로 60초를 기다렸는데, 이 PC의 상주 부하로는 충족되지 않았습니다.
  - 상위 세션의 요청으로 다음 조건으로 완화했습니다: 전체 3코어 미만, 1코어 이상 쓰는 단일 프로세스 없음, 15초 연속.
  - 상주 프로세스나 설정은 건드리지 않았습니다.
- **게임 실행 중 측정은 버렸습니다**
  - 오전 7~8시 측정(`mid-*`)에는 `witcher3`가 코어 약 5~8개를 쓰고 있었습니다.
  - 같은 조건에서 측정값이 3배 넘게 흔들렸으므로 판정에 쓰지 않았습니다.
- **반복 측정에 섞인 잡음**
  - `final-*` 반복 측정 내내 제가 실행한 `find` 디스크 검색이 코어 1개를 쓰며 돌았습니다.
  - `final-mixed-2`는 튀는 값이 있어 판정에서 뺐습니다.
- **흔들리는 폭**
  - 혼합 세트 ZIP 압축은 0.13~0.2초대라 측정 시간이 짧아 잡음 비중이 큽니다.
- **Defender와 새로 빌드한 exe**
  - 새로 빌드한 `target\release\nz.exe`는 같은 코드의 복사본보다 해제가 2배 넘게 느렸습니다(1.39 s 대 0.60~0.63 s).
  - 원인은 Defender가 새 exe를 검사하기 때문으로 보입니다.
  - 그래서 모든 측정은 스크래치패드로 복사한 exe로 했습니다.
  - 이전 세션에서 이 효과를 모르고 비교한 K5b 개선 시도(폴더별 병렬 쓰기, 디코딩 비용 순 정렬)는 "느려졌다"고 판단해 되돌렸습니다. 그 비교는 무효이고 재시험 후보입니다(5장).

## 3. 게이트별 상세

### 압축 (K1, K1b, K2, K4)

1차 측정(`clean-*`) 기준입니다.

| 세트 | 케이스 | 시간, 압축률 |
|---|---|---:|
| 텍스트 | zip:5 압축 | 0.059 s, 50.98% |
| 텍스트 | 7z -l:6 | 1.045 s, 45.16% |
| 혼합 | zip:5 | 0.161 s, 68.87% |
| 혼합 | 7z -l:6 | 3.271 s, 62.15% |

7z 속도가 더 오르지 않는 이유:

- 시간의 대부분은 LZMA2 normal 모드(최적 파싱)가 차지합니다.
- 텍스트 15 MB 하위 집합으로 압축률을 거의 지키는 설정을 찾아봤습니다.

| 설정 | 크기 | CPU 시간 | 비고 |
|---|---:|---:|---|
| 현재 (-l:6) | 1,140,477 B | 3.43 s | |
| `-depth:16` | 1,145,606 B | 3.18 s | |
| `-nice:64 -depth:8` | 1,184,764 B | 2.23 s | +3.9%, 압축률 예산 초과 |

- 두 조건(압축률 유지, 큰 폭의 속도 향상)을 함께 만족하는 조합은 찾지 못했습니다.
- 혼합 세트의 실행 파일 클래스는 4 MiB preload가 있어야 압축률이 유지됩니다.
- 이번 브랜치에서 혼합 7z:6 크기가 65,381,644 → 65,329,709 B로 조금 줄었습니다. ZIP 계열 클래스의 zstd 창을 데이터 크기에 맞춘 효과입니다.

### K3

- `-l:9` 결과: 12,900,957 B (44.93%), 15.6 MB/s. 압축률과 속도 모두 미달입니다.
- 결정 A(표준 7z 유지, precomp나 NextZip 전용 코더 없음)에 따라 미달로 둡니다.
- **원인**
  - 텍스트 세트에 들어 있는 `.sla` 파일 12.25 MB는 내용이 이미 zlib 레벨 6 스트림입니다.
  - 표준 LZMA2로는 더 줄지 않습니다.
- **precomp 추정**
  - `.sla`를 inflate한 뒤 xz로 압축하면 12.25 MB → 3.27 MB가 됩니다.
  - 세트 전체로는 약 18~20%가 될 것으로 추정합니다.
  - 단, 이렇게 만든 아카이브는 다른 7z 도구로 풀 수 없습니다.
- **PPMd 시도**
  - 7z 표준 코더라 호환성 문제는 없습니다. 옵션 `-ppmd:<order>`, `-ppmdmem:<MiB>`, `-pblock:<KiB>`로 넣었습니다.
  - 텍스트 세트 결과가 13.36 MB와 13.21 MB로 LZMA2보다 나빠서 기본값으로는 쓰지 않습니다.

### K6

- **파일 형식**
  - `tar.zst`를 64 MiB 단위의 독립 zstd 프레임으로 씁니다(`tarzst::FRAME_BYTES`).
  - 해제기 `parzst::ParZstd`가 프레임 헤더를 훑고 여러 프레임을 병렬로 디코딩합니다.
  - 출력은 작업자 수와 무관하게 바이트까지 같습니다(테스트로 확인).
- **실제 해제** (2,102,402,560 B 단일 파일 → `C:\nzbench-excl\k6out`, 5회 중앙값)
  - 1.010 s = **2.08 GB/s** (`1.0/k6-extract.log`)
  - 이전 세션에서 PC가 한가할 때 잰 값은 0.79 s(2.67 GB/s)였습니다.
  - 단일 프레임 아카이브는 1.35~1.7 s였습니다.
- **디코딩만** (`zstdbench`, `1.0/k6-decode.log`)
  - 병렬 2.35~4.42 GB/s, 순차 1.3~2.3 GB/s
  - 이전 세션의 한가한 시점 측정은 4.5~4.9 GB/s였습니다.
- **병목**
  - 2.1 GB짜리 파일 하나를 순차로 쓰는 단계가 병목입니다.
  - NTFS에서는 순서 없는 위치 쓰기가 valid-data-length 0 채우기 때문에 더 느렸고, 그래서 쓰기 스레드 하나로 순차 기록합니다.
- **비용**
  - 압축 크기가 +0.6% 늘었습니다(1,359,797,240 → 1,368,476,322 B).
  - 압축 시간도 늘었습니다(11.3 → 14.0 s). 다만 게임 실행 중에 잰 값이라 정확하지 않습니다.

### K9

- **새로 넣은 것** (`nz_core::mem`)
  - 기본 예산: 여유 물리 메모리의 절반을 256 MiB~1 GiB로 제한한 값. `NZ_MEM_MIB`로 덮어쓸 수 있습니다.
  - 7z 인코더: 바이트 세마포어(`Gate`)로 동시에 도는 LZMA2 세그먼트와 zstd 작업자 수를 제한합니다. 일괄 버퍼 크기도 예산에 맞춥니다.
  - tar.zst 해제: 동시에 디코딩 중인 프레임 수를 예산에 맞춥니다.
  - 예산은 실행 순서만 바꾸고 **출력 바이트는 바꾸지 않습니다**. 블록·세그먼트 크기는 입력과 옵션으로만 정해집니다.
- **측정 방법**: `nz bench`가 자식 프로세스마다 최대 working set과 commit을 기록합니다(새 열 "peak WS c/x MiB").
- **결과** (MiB, 압축 / 해제)

| 케이스 | working set | commit | 이전 (main) WS / commit |
|---|---:|---:|---:|
| 혼합 7z:6 | 683~730 / 194 | 972~980 / 248 | 1005 / 1403 |
| 텍스트 7z:9 (K3) | 572 / 48 | 871 / 59 | 1603 / 2134 (혼합 7z:9) |
| 혼합 zip:5 | 131~138 / 30 | 146~155 / 32 | 122 / 138 |
| 혼합 tar.zst:5 | 185 / 60 | 381 / 58 | (main에서 측정) |

- working set은 모두 1 GB 미만입니다.
- commit은 1 GiB 미만이지만, 10^9 바이트 기준으로는 약 1.03 GB입니다. KPI의 "1 GB"가 commit 기준이라면 예산 상한을 줄여야 합니다(한 줄 변경).

### 6.1 tar 숫자 필드 (0187c7e)

- **방식**
  - `tar` 크레이트 앞에 `tarfix::TarFix` 리더를 둡니다.
  - 이 리더는 블록 구조를 따라갑니다: 헤더, PAX `size`, GNU sparse 확장 블록(데이터보다 먼저 옴), 패딩된 데이터, 끝 표시(0 블록 2개) 뒤는 그대로 통과.
  - 크레이트가 거부하는 size/mtime 필드만 libarchive 방식으로 읽어 다시 씁니다(앞 NUL은 0, 뒤쪽 쓰레기는 무시).
  - 원래 체크섬이 맞았던 경우에만 체크섬을 다시 계산합니다.
  - 데이터는 추가 복사 없이 넘깁니다.
- **결과**
  - `empty_with_gnulabel`: 오류 없이 빈 아카이브로 열림(libarchive 기대와 같음).
  - `timestamp_overflow`: `tmp/f.txt`(0 B)로 풀림.
- **회귀 확인**
  - libarchive 코퍼스의 tar 계열 54개를 이전 빌드와 비교했습니다. 바뀐 것은 `timestamp_overflow` 하나뿐이고, 나머지 53개는 같은 트리가 나옵니다.
  - 중간 버전에서 sparse 1.13/1.17 결과가 달라지는 버그가 있었는데, 고친 뒤 회귀 테스트로 넣었습니다.
- **테스트**: 단위 테스트 5개. 그중 `corpus_passes_through_unchanged`는 `NZ_TAR_CORPUS`를 지정하면 코퍼스 전체를 검사합니다.

### 6.2 K9: 예산 상한 880 MiB (3a5d313)

- **원리**: 최대 commit은 예산에 최대 약 20 MiB를 더한 값을 따라갑니다. 혼합 세트에서 예산별로 잰 commit은 다음과 같습니다.

| 예산 (MiB) | 7z:6 commit | 7z:9 commit |
|---:|---:|---:|
| 1024 | 969 | 957~1021 |
| 896 | 858 | 911 |
| 800 | 756 | 821 |
| 704 | 691 | 724 |

- **출력**: 어느 예산에서도 출력 바이트는 같습니다.
- **함께 바꾼 것**
  - 7z의 zstd 작업자 수를 게이트 용량의 1/3이 아니라 1/2로 계산합니다. 1024 → 928 MiB 사이에서 level 19 작업자가 2개에서 1개로 줄어 7z:9가 약 1.6배 느려지던 절벽을 없앴습니다.
  - LZMA2 세그먼트 출력에서 쓰지 않은 용량을 반납합니다. commit이 20~40 MiB 줄었습니다.
- **비용**: 7z:9는 2개 → 1개 작업자 절벽은 피했지만, 텍스트 7z:9가 약 10~30% 느려졌습니다. K3 속도가 15.6 → 11.4 MB/s가 된 원인입니다. K3는 결정 A로 이미 미달입니다.
- **효과**: 7z:6(게이트 대상) 속도는 변화가 없습니다.

### 6.3 K5b 재시험 (`1.0/k5b-retest.txt`)

- **방법**: 복사한 exe 하나에 임시 스위치를 넣어, 네 모드를 번갈아 실행했습니다(7회와 15회). 비교한 모드는 기존 방식, 비용 순 정렬, 폴더 내 병렬 쓰기, 둘 다입니다.
- **결과**
  - 병렬 쓰기는 5~10% **느려졌습니다**. 파일 시스템 경합 때문으로 봅니다.
  - 비용 순 정렬은 잡음 범위 안에서 차이가 없었습니다.
- **조치**: 채택하지 않았습니다. K5b는 이미 목표를 충족해 여유가 있습니다.

### 6.4 K5 엔진 (`1.0/k5-engine.txt`)

- **반복 측정**: 예외 폴더에서 7회 측정을 5번 했습니다. nz 실행 시간이 0.19~0.25 s와 0.38~0.69 s 두 무리로 갈립니다. 최선은 0.193 s입니다. 판정은 **미달**입니다.
- **원인**
  - 12스레드의 스레드 시간을 합하면 압축 해제 0.27 s, 파일 생성 0.66~1.77 s, 쓰기 0.75~1.03 s, 닫기 0.33~0.43 s입니다.
  - 즉 일의 약 85%가 파일 1,444개의 NTFS 생성·쓰기·닫기입니다. 파일 시스템 자체가 바닥입니다.
- **경로 비교**
  - `nz x`는 `nz-archive`의 ZIP 해제를 씁니다. 이 경로는 파일마다 `create_dir_all`을 호출하고, 미리 확장(`set_len`)하지 않습니다.
  - nz-core의 `zip::extract_zip`(디렉터리를 한 번에 만들고 미리 확장)과 번갈아 15회 비교했더니 nz-core 쪽이 4~8% 빠릅니다.
  - `nz-archive`는 포맷 확장 세션 소관이라 손대지 않았습니다. **제안**: `nz-archive`의 ZIP 해제를 `nz_core::zip::extract_zip`처럼 바꾸면 4~8%를 얻습니다. 다만 그것만으로 큰 차이는 나지 않습니다.

### 6.5 압축 속도 향상 시도

**ZIP (K1, K1b)**

- **텍스트 단계별 시간** (`NZ_TRACE`): 탐색 4 ms, 압축 약 40 ms, 쓰기 꼬리 약 7 ms, 프로세스 고정 비용 8.7 ms(파일 하나 압축의 중앙값).
- **레벨 낮추기**: libdeflate 레벨을 6에서 4/3/2/1로 낮춰도 0.057 s → 0.053 s로 거의 빨라지지 않습니다. 반면 dl=4부터 크기(14,797,348 B)가 압축률 예산(14,712,316 B)을 넘습니다. 시간의 대부분이 Deflate 연산이 아니라 파일 1,211개의 열기·읽기와 고정 비용이라는 뜻입니다.

**7z 혼합 (K4)**

- **병목**: 클래스별 시간은 text 3블록, exec 1블록 3.0~3.2 s, other 2블록, zip(zstd) 1블록 1.3 s입니다. CPU 시간 18.7 s에 벽시계 3.03 s라 평균 6.2개 스레드만 일합니다.
- **핵심 경로**: exec 블록입니다. 4 MiB 세그먼트마다 4 MiB preload를 다시 처리해서 세그먼트 하나에 2.5~3 s가 걸립니다. 메모리 게이트 탓은 아닙니다(예산 4000 MiB에서도 3.10 s).
- **exec 세그먼트·preload 줄이기**

| 설정 | 크기 | 시간 | 예산(65,607,307 B) 대비 |
|---|---:|---:|---|
| 기본 | 65,329,709 | 2.82 s | 충족 |
| eseg 2048, epre 2048 | 65,796,731 | 2.62 s | **초과** |
| eseg 2048, epre 1024 | 66,124,193 | 2.38 s | **초과** |
| eseg 1024, epre 1024 | 66,271,869 | 2.46 s | **초과** |

- **preload를 유지한 채 세그먼트만 줄이기** (eseg 2048/1536/1024): 빨라지지 않았습니다. 각 세그먼트가 preload를 다시 처리하기 때문입니다.
- **other 클래스**(`-onice:32`, `-odepth:16`, `-xlo:5`): 1~7% 범위로, 잡음 수준입니다.
- **결론**: exec 클래스는 4 MiB preload가 있어야 압축률이 유지되고, 그 preload가 핵심 경로를 만듭니다. 압축률 조건 안에서는 지금 속도(약 2.8 s) 근처가 한계로 보입니다.
- **남은 후보**: exec를 별도 폴더로 나누는 방식 등 근본적인 재설계가 필요합니다. 예를 들어 preload 대신 이전 세그먼트 끝에서 딕셔너리 상태를 이어받는 직렬-병렬 혼합 방식입니다.
