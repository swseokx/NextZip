## 1. 만든 것

| 항목 | 위치 | 내용 |
|---|---|---|
| .nz v1 사양 | `docs/nz-format-v1.md` | 헤더, 블록, 인덱스, 복구 기록, 암호화, 트레일러, 백업 추가 절차, 읽기 규칙, 테스트 벡터. 벡터는 `crates/nz-nzf/tests/spec_vectors.rs`가 구현으로 다시 만들어 바이트 단위로 비교합니다. |
| 참조 구현 | `crates/nz-nzf` (MIT, 새 크레이트) | 생성, 추출, 목록, 검사, 복구(repair), 백업 추가, 스냅숏 복원 |
| CLI | `crates/nz-cli` (`nz_cmd.rs` 새 파일, `main.rs`, `archive_cmd.rs`, `bench.rs`) | `nz c -fmt:nz` 또는 `*.nz`, `x`, `l`, `t`, `repair`, `backup`, `snapshots`, `restore`, `nz bench`의 `nz:<level>[:rr=N]` 케이스 |
| 퍼즈 타깃 | `fuzz/fuzz_targets/nz_read.rs`, `nz_recovery.rs` | 리더 전체 경로와 복구 경로만 따로 |

포맷의 주요 결정 (사용자 확인 사항):

- **복구 예산:** 섹터 단위로 보장합니다. 섹터 크기 S는 1–4 KiB이고, 32768섹터 묶음마다 패리티는 `max(1, ceil(D·bp/10000))`입니다. 한 묶음에서 손상된 섹터(데이터와 패리티 합) 수가 그 묶음의 패리티 수 이하이면 완전히 복원됩니다. 복구 기록 자신의 해시 표와 헤더는 두 벌씩 둡니다.
  - 리드-솔로몬은 Leopard 방식 GF(2^16) 고율 부호(`reed-solomon-simd` 3.1)입니다.
  - 기본값은 `-rr:3`(3%)입니다.
- **백업:** 한 .nz 파일 끝에 추가합니다. 기존 인덱스 끝까지 자른 뒤 중간 헤더를 먼저 써서, 도중에 멈춰도 직전 스냅숏이 유효하게 남습니다. 그 뒤 새 청크 블록, 전체 새 인덱스, 복구 기록, 인덱스 사본, 트레일러를 씁니다.
- **청크 분할:** FastCDC 16 KiB / 64 KiB / 256 KiB를 씁니다. 기어 표는 BLAKE3로 만들어 사양에 고정했습니다. 중복은 BLAKE3 해시로 찾고, 암호화했을 때는 키가 걸린 BLAKE3를 씁니다.
- **암호화:**
  - Argon2id (기본 64 MiB, t=3, p=1. 읽는 쪽 한도는 m≤1 GiB, t≤64, p≤16)
  - AES-256-GCM 또는 ChaCha20-Poly1305
  - 파일 이름을 포함한 인덱스까지 암호화합니다.
- **레벨별 코덱:**

  | 레벨 | 코덱 | 블록 크기 |
  |---|---|---|
  | 0 | 저장 | — |
  | 1 | LZ4 | — |
  | 2–6 | zstd 1/3/5/6/9 | 4 MiB |
  | 7–8 | zstd 15/19 | 16 MiB |
  | 9 | LZMA2 프리셋 9 (`lzma2_parallel`로 체인 병렬 인코딩) | 64 MiB |

  압축해도 줄지 않는 블록은 저장으로 떨어집니다.
- **결정성:** 출력은 스레드 수와 상관없이 같습니다. 테스트에서 1, 3, 8 스레드의 바이트를 비교했습니다. 복구 기록의 줄무늬 병렬 부호화도 결과 바이트가 같습니다.

## 2. 테스트

`nz-nzf` 테스트는 모두 통과합니다.

- **단위 테스트 7개:** cdc, rr 줄무늬 결과가 전체 부호화와 같은지, 여러 묶음 복원 등.
- **통합 테스트 10개** (`tests/nz.rs`):
  - 레벨 0–9 왕복
  - 스레드 수에 따른 결정성
  - 암호 두 종류, 틀린 비밀번호
  - 백업 중복 제거와 모든 스냅숏 복원, 암호화된 백업
  - **무작위 손상(예산 안):** 24회. 비트 반전, 0으로 덮기, 연속 구간 손상을 섞었고 전부 완전히 추출됐습니다.
  - **구조 위치 손상:** 14가지. 헤더, 트레일러, 블록 헤더, 인덱스, 복구 기록 헤더와 해시 표, 패리티, 잘라내기를 다뤘고 전부 완전히 추출됐습니다.
  - **예산 초과 손상:** 복원 실패 묶음과 손상된 파일이 보고됩니다.
  - **복구 기록이 없을 때:** 손상을 보고합니다.
  - `repair` 명령으로 아카이브를 다시 쓰기.
- **`spec_vectors`:** 문서의 hex 벡터 3개(plain, index-body, recovery)가 구현과 일치합니다.
- **`fuzz_smoke`:** 씨앗 7개(암호화와 백업 포함)에 무작위 변형을 넣어도 패닉이 없습니다.

### 4.3 해석

- **속도:** nz:5는 7z:5보다 4.5–7배 빠르게 압축합니다. 대신 비율이 4–7%p 높습니다(덜 압축됨).
  - 3%p 안팎은 복구 기록 3%에서 오고, 나머지는 zstd 6과 LZMA2의 차이입니다.
- **nz:9:**
  - 복구 기록이 없으면 7z:5와 비슷한 비율(text 45.62% 대 45.83%, mixed 62.58% 대 62.46%)입니다.
  - 압축 시간은 7z:9의 0.57–0.66배입니다.
  - 압축 메모리가 큽니다(mixed 1.6 GiB). 64 MiB 블록을 여러 개 병렬로 처리하기 때문입니다.
- **추출:** 같은 비율대의 7z보다 느립니다.
  - text 세트는 작은 파일이 많아 파일 생성 비용이 대부분입니다.
  - nz:9의 mixed 추출 2.6 s는 LZMA2 디코딩이 블록당 단일 스레드이기 때문입니다.
  - 남은 과제로 적었습니다.

## 7. 남은 것과 후속 과제

1. **GUI와 셸에서 .nz 열기:** nz-archive에 `Kind::Nz`와 목록·추출 경로를 등록해야 합니다. 이는 M5 소유 크레이트라 손대지 않았고, 지금은 CLI에서만 .nz를 다룹니다.
2. **ADS와 xattr:** 포맷(Entry의 streams)에는 정의돼 있지만 CLI가 아직 수집하지 않습니다.
3. **압축률 격차:**
   - nz:5는 7z:5보다 4–7%p 덜 압축됩니다.
   - 개선 방안 후보로 기본 레벨 매핑 재조정, 레벨 6–8에 LZMA2 도입, 확장자별 정렬 외의 묶음 전략이 있습니다.
4. **추출 속도:** 작은 파일이 많을 때의 생성 비용, 그리고 레벨 9 블록 단위 LZMA2 디코딩을 개선할 수 있습니다.
5. **퍼즈 처리량이 낮습니다(33–111 실행/초).**
   - 씨앗이 작은데도 Argon2와 복구 기록 디코딩이 비쌉니다.
   - 타깃을 더 잘게 나누면 효율이 오를 것입니다.
6. **이번 작업과 무관한 기존 실패** (`m4-nz`에서도 main과 같은 코드인 nz-archive):
   - `tests/isolation.rs` 3개: 테스트용 `*.zip`과 `t.tar.zst`가 `.gitignore`에 걸려 새 워크트리에 없습니다.
   - `tests/hang.rs`의 `decoder_panic_is_an_error`: 2 GiB 할당 실패(0xc0000409)로 끝납니다.
