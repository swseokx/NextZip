## 1. 한 일

### 1.1 AMSI 연동 (스펙 9 "AMSI 연동(별도 프로세스), 해제 전 검사 옵션")

- 새 크레이트 `nz-scan`: AMSI(`AmsiScanBuffer`)를 **별도 프로세스**에서 부르는 검사기와 프레임 프로토콜. 8 MiB 창을 64 KiB 겹쳐 큰 파일도 검사(경계에 걸친 EICAR도 감지), 프로세스 풀(최대 4개).
- 검사기 실행 파일은 따로 배포하지 않고 `nz-decode.exe --scan`이 겸합니다(설치 파일 변경 없음).
- `nz-archive` 해제 경로별 처리 (`src/scan.rs`):
  - ZIP·ALZ·EGG: 메모리에서 푼 항목을 **쓰기 전에** 검사.
  - 격리 디코더 경로(RAR, 레거시 형식, ZIP AES 등): 받은 데이터를 메모리에 모으며 검사하고, 깨끗할 때만 씀. 64 MiB를 넘는 항목만 `이름.nzpart`로 디스크에 두었다가 이름을 바꿈.
  - nz-core 경로(7z 기본, tar 계열): 해제 뒤 새로 생기거나 바뀐 파일을 검사, 감지되면 지움.
  - 감지된 항목은 쓰지 않고 나머지는 풀며, 끝에 `ArchiveError::MalwareFound(이름들)`로 실패.
  - AMSI를 못 쓰면(공급자 없음·정책) 알림(`Progress::notes`)만 남기고 검사 없이 풂.
- 설정: `malware_scan` (기본 켜짐). GUI 설정 메뉴, CLI `-noscan`/`-scan`, 설정 파일 `%LOCALAPPDATA%\NextZip\settings.txt`.
- UI: 감지 시 GUI는 경고 창("NextZip - 악성코드 발견" + 파일 이름 + Windows 보안 안내), 진행 창 실패 메시지, CLI는 오류 메시지와 종료 코드 1.
- 테스트: EICAR 문자열은 실행 중에 조립하고, 테스트 압축 파일은 ZipCrypto·WinZip AES로 암호화해서 **저장소와 디스크에 평문 EICAR이 없습니다.** Defender가 저장소 파일을 격리한 일은 없었습니다.
  - `nz-scan/tests/eicar.rs` 4개, `nz-archive/tests/malware.rs` 4개(메모리 경로, 격리 경로, 깨끗한 파일, 검사 끔).
  - 첫 구현에서는 격리 경로가 검사 전에 `.nzpart`에 평문을 써서 Defender가 `%TEMP%`의 테스트 임시 파일을 잡았습니다. 메모리 보관 방식으로 고친 뒤에는 AMSI 감지 기록만 남습니다.
  - 테스트를 돌리면 Defender가 "위협 발견" 알림을 띄우고 보호 기록에 EICAR 감지가 남습니다(AMSI 감지 = 정상 동작).

### 1.2 안정성 버그

- **손상된 HA 입력이 릴리스에서 폭주**: 원인은 unarc-rs HA ASC/HSC 디코더가 기록된 크기를 무시해 릴리스에서 무한 출력(약 35 MB/s, 한 테스트는 68 GB까지 메모리 증가). `third_party/unarc-rs` 패치로 기록된 크기를 넘으면 실패 → 두 손상 입력 모두 1초 안에 실패. 백업으로 격리 디코더 자식에 시간·메모리 감시(`isolated::watchdog`) 추가. `docs/upstream-bugs.md`에 기록(외부 보고 안 함).
- **`decoder_panic_is_an_error` 디버그·릴리스 모두 유효**: 테스트 분리(같은 프로세스의 stall 한도 공유 문제)와 위 패치로 해결.
- **MSRV 통일**: unarc-rs(delharc 0.8)가 Rust 1.95를 요구하므로 워크스페이스·clippy·nz-formats 모두 1.95로 통일. 새 clippy 경고는 수정.
- **릴리스 전용 실패**: `.gitignore`가 `*.zip` 등 테스트 데이터를 빼고 있어 `nz-formats/tests/data`가 빠져 있던 문제(예외 규칙 추가, 파일 복원)와 HA 폭주가 원인이었음.

### 1.7 D2·D5 (후속 요청)

- D2: nz-core에 `extract_with(…, &ExtractOptions)`(최대 출력량, 최대 항목 수, 이름 훅)와 `LimitExceeded` 오류를 추가했습니다. nz-archive는 tar 계열에 격리 경로와 같은 상한(압축 파일 × 4096 + 1 GiB, 최대 64 GiB)을 넘기고, 넘으면 "압축 폭탄 의심: 출력이 한도를 넘었습니다"로 멈춥니다. 검사는 항목 헤더 크기로 쓰기 전에 합니다. 테스트 `tar_output_over_the_limit_is_rejected`.
- D5: ZIP·ALZ·EGG에서 동시에 메모리에 푸는 항목의 선언 크기 합계를 2 GiB(`MEMORY_BUDGET`)로 제한합니다. 넘으면 앞 항목이 끝날 때까지 기다리고, 2 GiB보다 큰 항목 하나는 혼자 실행합니다.
- nz-core 수정(M4 영역): `lib.rs`에 `ExtractOptions`·`NameHook`·`LimitExceeded`·`extract_with`, `tarfam.rs`에 `extract_tar_with`와 `extract_tar_stream`의 옵션 인자. 기존 `extract`·`extract_tar`는 제한 없이 그대로 동작합니다.

### 1.8 D1·D3·D4·D7 (사용자 결정 반영)

- **D1 링크 → 대상 경로 텍스트 + 실제 링크 옵션.** tar 계열과 격리 경로(RAR, LHA 등)의 심볼릭·하드 링크는 기본으로 "대상 경로 문자열을 담은 작은 텍스트 파일"로 풉니다.
  실제 링크는 설정(GUI 설정 메뉴 "tar의 심볼릭 링크를 실제 링크로 풀기", `settings.txt`의 `symlinks`, CLI `-symlinks`)을 켰을 때만 만들며 기본은 꺼짐입니다.
  - 대상이 풀 폴더 밖이면 두 경우 모두 만들지 않고 경고합니다. 대상이 빈 링크는 건너뜁니다.
  - LHA의 "이름|대상" 꼴 링크를 이름과 대상으로 나누도록 nz-formats를 고쳤습니다.
  - 테스트는 `links_become_text_files_by_default`이고, 기존 링크 탈출 테스트는 `symlinks: true`로 돌립니다.
- **D3 항목 수 상한 = 압축 파일 바이트 수 + 10,000.** 넘으면 쓰기 전에 "압축 폭탄 의심: 항목 수가 한도(N개)를 넘습니다"로 멈춥니다.
  - ZIP·ALZ·EGG·7z·격리 형식은 목록 단계에서, tar 계열은 스트리밍 중 헤더를 셀 때 검사합니다(`nz_archive::max_entries`).
  - 근거: 진짜 항목은 헤더와 이름 때문에 1바이트보다 싸게 담을 수 없습니다. 측정 결과는 다음과 같습니다(1바이트당 항목 수, 한도는 1.0 + 1만 개).

    | 대상 | 개수 | 가장 높은 값 | 한도 초과 |
    |---|---|---|---|
    | cargo 캐시의 실제 crate(.crate = tar.gz) | 307개 | 0.0036 (thiserror-2.0.18) | 0 |
    | 저장소 테스트 픽스처(모든 형식) | 96개 | — | 0 |
    | 빈 파일 10만 개(+폴더 100개), `-l:9` | zip·7z·tar.zst·tar.xz·tar.gz·tar.bz2 | 0.865 (7z, 115,663바이트) | 0 |
    | 1바이트 파일 5만 개(+폴더 50개), `-l:9` | 같은 6형식 | 0.897 (7z, 55,800바이트) | 0 |

    합성 12개는 실제로 풀어 봐도 모두 성공했습니다. 가장 빡빡한 경우(7z 헤더 압축)도 한도의 90% 정도라, 1바이트당 1개를 유지했습니다.
    더 작게(예: 0.5) 잡으면 빈 파일이 아주 많은 7z·tar.xz가 걸립니다.
  - 테스트: `tar_entry_and_size_limits`.
- **D4 C 코덱은 주 프로세스에 두고 퍼징 보강.** cargo-fuzz 타깃 3개를 추가해 14개가 되었습니다(`oss-fuzz/build.sh`에도 등록).
  - `core_tar`: nz-core tar 계열. 첫 바이트로 gzip, bzip2, xz, zstd, lz4, 무압축 중 하나를 고르고, 서명이 없으면 붙여서 넣습니다.
  - `core_7z`: nz-core 7z 리더(liblzma의 LZMA·LZMA2, libdeflate).
  - `codecs`: ZIP·7z 항목이 쓰는 원시 디코더 `inflate_exact`·`lzma2_decode`·`lzma1_decode`. 선언 크기와 속성을 입력에서 가져옵니다.
  - 시드는 `tests/fuzz_smoke.rs`의 `core_codec_mutations`가 만들고 돌연변이 스모크도 돌립니다.
  - 실제 퍼징(ASan, 빈 코퍼스, 타깃마다 90초): codecs 409,372회, core_tar 13,476회, core_7z 2,248회 모두 충돌·OOM 없음. Windows에서는 MSVC의 `clang_rt.asan_dynamic-x86_64.dll`이 있는 폴더를 그 프로세스의 PATH에만 넣어야 실행됩니다(설치·시스템 설정 변경 없음).
  - 작업 중 발견해 고친 것: 7z 헤더의 LZMA/LZMA2 사전 크기(최대 4 GiB)를 liblzma가 디코더를 만들 때 통째로 할당하고 있었습니다. 몇 바이트짜리 위조 7z가 4 GiB 메모리를 요구할 수 있었습니다.
    이제 사전 크기를 "출력 크기(최소 4 KiB)"로 줄여서 넘깁니다. 원시 스트림은 자기 출력보다 먼 곳을 참조할 수 없어 결과는 같습니다.
    nz-core `lzma.rs`의 `decode_dict`와 테스트 `huge_dictionary_in_header_is_not_allocated`가 이 부분입니다.
- **D7 암호 제로화(zeroize 크레이트).** 새 의존성은 `zeroize` 1.9.2(라이선스 MIT OR Apache-2.0)입니다. 이미 다른 크레이트를 통해 Cargo.lock에 있던 버전이라 새로 받은 코드는 없습니다. `aes` 크레이트의 `zeroize` 기능도 켰습니다.
  - 지우는 것: ZipCrypto 키(`ZipCrypto` Drop), AES 파생 키·키스트림·카운터(`AesKeys`·`AesCtr` Drop, PBKDF2 출력 버퍼), AES 키 스케줄(`aes` 기능).
  - 격리 프로세스: 요청 JSON 버퍼를 부모는 쓴 뒤, 자식은 파싱 뒤 지웁니다. `Request` Drop도 지웁니다.
  - 프런트엔드: `Options::forget_password()`를 GUI 작업자와 CLI가 해제 뒤 부릅니다. GUI 작업자가 stdin으로 받은 암호 줄도 지웁니다.
  - 남는 사본(우리가 못 지우는 것): nz-formats 내부 디코더가 가진 암호 사본, GUI 주 창이 한 세션 동안 기억하는 암호, HMAC 내부 상태, 그리고 `String` 재할당 때 남은 옛 버퍼입니다.

## 4. M4 세션에 알릴 것 (nz-core 최소 수정)

- `walk.rs` `safe_relative`: `.. `·`...` 거부, 끝 점·공백 제거, `:`·NUL 거부, 예약어 `_` 접두사(`is_reserved_name` 추가) + 테스트.
- `tarfam.rs`: `through_link` 추가, `resolve_inside`가 기존 링크를 거치는 경로와 `.. ` 꼴 구성요소 거부, `make_link`가 링크 안에 링크를 만들지 않음 + 테스트 수정.
- `hdeflate.rs`: `chunks_exact` → `as_chunks`(MSRV 1.95 clippy).
- `sevenz.rs`, `zip.rs`: clippy `collapsible_if` 자동 수정.
- `nz-sys`: `ui_language()`, `current_commit()` 추가.
- `lib.rs`: `ExtractOptions`(`max_total`, `max_entries`, `on_name`, `symlinks`), `NameHook`, `LimitExceeded`, `extract_with`. 기존 `extract`·`extract_tar`는 제한 없이, 실제 링크를 만드는 동작 그대로입니다(라운드트립 도구용).
- `tarfam.rs`: `extract_tar_with`, 항목 수·선언 크기 합계 집계, 이름 훅, `make_link`가 `symlinks: false`면 대상 경로 텍스트 파일을 씀.
- `lzma.rs`: `decode_dict`. 디코더 사전 크기를 출력 크기로 제한(위조 7z 헤더의 4 GiB 할당 방지) + 테스트.

## 5. 알려진 한계

- nz-core 경로의 사후 검사·MotW는 같은 크기·같은 시각으로 덮어쓴 파일을 놓칠 수 있습니다.
