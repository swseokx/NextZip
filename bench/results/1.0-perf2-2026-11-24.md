## 2. 변경: 7z 인코딩 작업 스케줄러 (`nz-core`)

**원인**

- 혼합 7z의 프로세스 CPU 시간은 약 19 s(user 15 s), 벽시계는 2.8~3.5 s였습니다. 평균 6~7개 논리 CPU만 일했습니다.
- 블록이 중첩된 Rayon 작업으로 돌아서 큰 작업이 먼저 시작된다는 보장이 없었습니다.
- 특히 x86 코드 블록(19 MB, 4 MiB 세그먼트 + 4 MiB preload 5개)은 세그먼트 하나가 경합 상태에서 2.5~3 s 걸리는 핵심 경로인데, 늦게 시작되는 경우가 많았습니다.

**방식** (`sevenz::encode_batch`, `lzma::SegPlan`, `lzma::splice`)

1. 배치의 블록을 큰 순서로 병렬로 읽습니다(CRC, BCJ 포함).
2. 모든 LZMA2 세그먼트와 블록 단위 작업(zstd, PPMd, Deflate)을 목록 하나에 넣습니다.
3. 예상 비용이 큰 순으로 정렬하고, 풀의 스레드가 원자 카운터로 앞에서부터 가져갑니다(LPT).
   - 비용 모델: `segbench`로 잰 MiB당 단일 스레드 비용입니다. x86 코드는 인코딩 270 / preload 78 ms, 텍스트는 127 / 30 ms, 기타(lc0)는 250 / 30 ms입니다.
   - 멀티스레드 zstd는 맨 앞에 둡니다. 내부 스레드가 LZMA2와 겹쳐 돌게 하기 위해서입니다.
4. 결과를 세그먼트 순서대로 이어 붙입니다.

**결정성**: 세그먼트 경계와 preload는 입력과 옵션으로만 정해집니다. 그래서 어떤 스레드가 언제 돌려도 바이트가 같습니다.

- 새 테스트 `job_schedule_keeps_bytes_and_roundtrips`: 1/3/8스레드 결과가 같은지, 해제 결과가 원본과 같은지 확인합니다.
- 실데이터에서도 main 빌드와 md5가 같았습니다(혼합: 12스레드·3스레드, 텍스트).

**함께 바꾼 것**: zstd 작업자 수를 2 MiB 작업 개수 이하로 제한했습니다. 작은 프레임이 메모리 게이트를 쓸데없이 잡지 않게 하려는 것입니다. 바이트는 바뀌지 않습니다(zstd MT는 작업자 수 1 이상이면 출력이 같음).

**추적**: `NZ_TRACE_JOBS=1`이면 작업마다 시작 시각과 소요 시간을 출력합니다.

## 3. 시도했지만 넣지 않은 것

| 시도 | 결과 |
|---|---|
| x86 코드 `nice` 128→64, depth 32/24, bt3, hc4n | 크기 변화는 ±0.1% 이내. 단일 스레드 세그먼트 시간은 1.39 → 1.31 s(nice 64)로 작았고, 게임 실행 중이라 전체 효과를 검증하지 못해 보류 |
| x86 세그먼트 2048 / preload 6144 KiB | 크기 −19 KB(더 좋음), CPU는 약 +40%. 부하 상태 측정에서 더 느려 보류 |
| x86 세그먼트 3072 / preload 3072 KiB | 크기 +127 KB. 사전이 6 MiB로 작아져 손해 |
| 기타 클래스 `hc4n` / `bt4f` / `hc4` | hc4n은 크기 같음, 시간 차이는 잡음 수준. bt4f·hc4는 텍스트 세트 +65 KB로 압축률 예산 초과 |
| ZIP `-dl:5` | 텍스트 14,702,997 B. 압축률 예산 대비 너무 빠듯해 보류 |
| K5: `nz-archive` ZIP 해제에서 디렉터리를 한 번에 만들고 `set_len` 미리 확장 | 9회 번갈아 잰 결과 0.260 → 0.279 s로 개선이 없어 되돌림 |
| K6: 2 GiB 순차 쓰기 방식 비교(버퍼, 무버퍼, 순차 힌트, 조각 크기) | 측정 중 0.3~1.06 GB/s로 크게 흔들림(다른 디스크 작업과 쓰기 캐시 상태). 결론을 낼 수 없어 코드 변경 없음 |

## 4. 프로파일 결과 (다음 작업용)

- **K1 (ZIP 텍스트)**
  - 프로세스 고정 비용: nz는 빈 실행 6.4~7.5 ms, 작은 압축 8.5~9.7 ms입니다.
  - 남는 시간은 Deflate CPU(`.sinc` 11 MB L6, `.sla` 10.7 MB L2)와 파일 열기·읽기입니다. 스레드 시간으로 읽기가 약 130~200 ms입니다.
  - 여기서 크게 더 줄이려면 6코어에서 CPU를 25% 이상 줄여야 해서, 지금 압축률 조건으로는 어렵다고 봅니다.
- **K2 (7z 텍스트)**
  - 일의 절반 이상이 `.sla`(12.25 MB, 이미 zlib 스트림)를 LZMA2로 압축하는 데 들어갑니다. 86.8%까지 줄어듭니다.
  - 압축할 수 없는 데이터에서 LZMA2는 약 4~5 MB/s로, 매치 파인더의 메모리 지연이 지배합니다.
  - 작업 22개가 2회전으로 나뉘어 꼬리가 약 10% 남습니다.
- **K4 (7z 혼합)**: 이제 x86 코드 세그먼트(단독 1.39 s, 경합 시 2.4~3 s)가 핵심 경로입니다.
  - preload(match finder skip) 비용이 인코딩의 약 30%입니다(4 MiB에 0.31 s).
  - x86 코드는 사전이 클수록 크게 좋아집니다(preload 6 MiB가 4 MiB보다 −19 KB).
- **측정 환경**
  - 이번 세션 동안 다른 세션의 빌드·테스트(3~6코어)와 게임(TslGame)이 오래 돌았습니다.
  - 그래서 탐색 단계의 수치는 대부분 상대 비교로만 썼습니다.
  - 최종 판정은 부하가 2코어 미만일 때 잰 값입니다.
