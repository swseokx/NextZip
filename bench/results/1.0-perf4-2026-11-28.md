# 1.0 성능 4차 (2026-11-28, 브랜치 `perf-4`)

- 대상: 아직 못 넘은 게이트 K1(ZIP 텍스트 압축), K1b(ZIP 혼합 압축), K5(ZIP 해제, 엔진 단독).
- 기준: main `f9012fd`(perf-3 병합). 비교: `perf-4` `8070e07`.
- 측정: 기준 빌드, perf-4, 비교 도구를 회차마다 번갈아 실행했습니다. 케이스마다 워밍업 1회와 7회 측정의 중앙값을 내고, 같은 조건으로 2회 반복했습니다. 12스레드입니다. exe는 스크래치 폴더로 복사해 실행했습니다.
- 해제 측정: 회차마다 출력 폴더를 지우고 1.5초 쉰 뒤 다음 회차를 돌렸습니다(모든 도구 같은 조건). 직전 회차의 삭제와 겹치면 0.4~1 s짜리 느린 회차가 생겨서 넣었습니다. 그래도 느린 회차가 일부 남습니다.
- 부하 조건: 측정 직전 5초 샘플에서 전체 0.79~1.43코어, 단일 프로세스 최대 0.51코어였습니다. 게임 실행 중(3.7코어)에는 기다렸다가 측정했습니다.
- 이 문서에는 NextZip의 절대 수치만 싣습니다. 비교 도구 수치는 싣지 않습니다. 원자료: `bench/results/1.0p4/gate.log`(비교 도구 행은 뺐습니다).

## 1. 게이트

게이트: 같은 실행에서 가장 빠른 비교 도구의 2배 속도, 압축률은 같거나 더 좋아야 합니다.

| KPI | 기준 빌드 (1회 / 2회) | perf-4 (1회 / 2회) | 변화 | 판정 |
|---|---:|---:|---|---|
| K1 ZIP 텍스트 압축 | 0.0516 / 0.0571 s | 0.0527 / 0.0574 s, 50.98% | 변화 없음 (코드 변경 없음) | 미달 (2회 모두) |
| K1b ZIP 혼합 압축 | 0.1230 / 0.1313 s | 0.1238 / 0.1288 s, 68.87% | 변화 없음 (코드 변경 없음) | 미달 (2회 모두) |
| K5 ZIP 해제, 엔진 단독 (Defender 예외 폴더) | 0.2195 / 0.1959 s | **0.2037 / 0.1851 s** | 약 5~7% 빨라짐 | 1회 충족, 2회 미달 → 미달 |
| (참고) K5 ZIP 해제, Defender 켜짐 | 0.1813 / 0.1694 s | 0.1724 / 0.1805 s | 잡음 범위 | 충족 (기준: 비교 도구보다 빠름) |

- 압축 결과 바이트는 main과 같습니다(텍스트 14,637,388 B, 혼합 72,391,199 B). 압축률은 비교 도구보다 좋습니다.
- K5 1회차는 비교 도구 쪽 느린 회차가 중앙값에 들어가 2배를 넘었고, 2회차는 넘지 못했습니다. 두 번 모두 충족해야 하므로 미달로 판정합니다.
- "Defender 켜짐" 행은 스크래치 폴더(사용자 임시 폴더 아래)에서 쟀습니다. 이번 측정에서는 예외 폴더보다 오히려 빨랐습니다. 이전 측정(0.376~0.393 s)과 폴더가 달라 직접 비교할 수 없습니다.

## 2. 변경 (K5)

### 2.1 해제 버퍼 재사용

- 이전에는 멤버마다 압축 데이터용과 풀린 데이터용 `Vec`을 새로 할당했습니다. 혼합 세트에서 약 180 MB의 새 페이지 폴트가 났습니다.
- 이제 해제 스레드마다 버퍼(`nz_core::zip::EntryBuffers`)와 libdeflate 해제기를 하나씩 두고 재사용합니다.
  - 버퍼는 필요한 만큼만 늘리고 0으로 다시 채우지 않습니다.
  - 64 MiB를 넘게 커진 버퍼는 쓰고 나서 놓습니다.
- 암호화된 멤버는 기존 경로를 그대로 씁니다.
- API: `read_entry_into`, `EntryBuffers`, `deflate::inflate_into`. `read_entry`와 `inflate_exact`는 그대로 남아 있고 내부에서 새 함수를 부릅니다.

### 2.2 이름 정리 한 번, 병렬로

- `plan()`은 멤버 이름마다 `sanitize`를 두 번 돌렸습니다. 이름 변경 알림을 만들 때 한 번 더 돌렸기 때문입니다. 1,444개 이름에 한 스레드로 약 5 ms가 걸렸습니다.
- 이제 해제 풀에서 한 번만 병렬로 돌리고, 알림은 그 결과로 만듭니다. 알림 문구와 오류 메시지는 같습니다.

### 2.3 이미 만든 폴더 건너뛰기

- 끝에 목록상의 폴더를 만드는 단계(`Dirs::finish`)가 이미 상위 폴더로 만들어진 폴더에도 `create_dir_all`을 불렀습니다.
- 이제 그런 폴더는 건너뜁니다. 꼬리 시간이 약 6 ms에서 0.8 ms로 줄었습니다.

### 2.4 단계별 효과 (최소값, 11회 × 3회 번갈아)

| 빌드 | 최소값 |
|---|---:|
| 기준 | 0.207~0.211 s |
| 2.2 + 2.3 | 0.198~0.201 s |
| 2.1 + 2.2 + 2.3 | 0.192~0.196 s |

## 3. 분석

### 3.1 K1b: 연산만으로 목표를 넘음

- 파일을 미리 메모리에 읽어 두고 ZIP 레벨 5 연산만 12스레드로 돌려도 혼합 세트는 87~102 ms가 걸립니다(`readbench` 예제).
- 프로세스 시작(약 6 ms), 폴더 탐색(약 5 ms), 읽기를 더하면 지금 시간(약 0.125 s)에 가깝습니다.
- 2배를 넘으려면 같은 압축률에서 Deflate CPU를 약 40% 줄여야 합니다. 이전 보고서대로 압축률 여유가 50 KB뿐이라 레벨을 낮출 수 없습니다.
- libdeflate를 `/arch:AVX2`로 빌드해 봤지만 연산 시간이 같았습니다.
- C 코덱 전체를 clang-cl(LLVM 23.1.6)로 빌드한 결과는 3.4절에 있습니다. 조금 빨라지지만 게이트를 넘기에는 한참 모자랍니다.

### 3.2 K1: 파일 열기가 병렬로 거의 안 됨

- 텍스트 세트 1,211개 파일을 12스레드로 **열기만** 해도 13~15 ms가 걸립니다. 한 스레드로는 24 ms입니다. 읽기까지 해도 시간이 같습니다. 열기가 사실상 직렬입니다.
- 폴더별로 묶어 열어도 같았습니다.
- 연산만 하면 25~30 ms(12스레드)이고, 실제 압축 단계는 31~40 ms입니다.
- 압축이 끝난 뒤 쓰기 스레드가 5~8 ms 더 돕니다. 다음은 모두 효과가 없었습니다.
  - 로컬 항목을 처리 순서(큰 파일 먼저)로 쓰기
  - 쓰기 스레드 우선순위 올리기
  - 텍스트 세트에도 매핑 쓰기 적용

### 3.3 K5: NTFS 파일 생성이 바닥

`fsbench` 예제는 해제 없이 같은 경로와 크기의 파일 1,444개(105 MB)만 만듭니다. 결과는 다음과 같습니다.

| 방식 | 시간 |
|---|---:|
| 파일마다 작업 하나 | 200~230 ms |
| 폴더 단위 작업 | 155~175 ms |
| 수정 시간 설정 | 20~30 ms 추가 (`SetFileTime`, 쓰기 전에 하든 별도 스레드에서 하든 같음) |
| `NtCreateFile`로 폴더 핸들 기준 상대 열기 | 이득 없음 |
| 생성 시 할당 크기 지정 | 이득 없음 |

- 실제 해제는 rayon이 작업을 연속 구간으로 나눠서 이미 폴더 단위에 가깝습니다. 그래서 폴더 단위 분배를 넣어도 빨라지지 않았습니다.
- 해제 병렬 구간은 12 논리 코어 중 약 4.5코어만 씁니다. 나머지는 파일시스템 대기입니다.
- 스레드 수를 바꿔도(12/16/24) 변화가 없었습니다.

### 3.4 C 코덱을 clang-cl로 빌드

- 방법: 같은 소스에 `CC_x86_64_pc_windows_msvc=<LLVM 설치 폴더>/bin/clang-cl.exe` 환경변수만 주고 빌드했습니다. 출력 바이트는 같습니다.
- 원자료: `bench/results/1.0p4/clang.log`. 기본 빌드(MSVC)와 번갈아 쟀고, 7회 중앙값을 2회 반복했습니다.

| 케이스 | MSVC (1회 / 2회) | clang-cl (1회 / 2회) |
|---|---:|---:|
| K1 텍스트 압축 | 0.0585 / 0.0637 s | 0.0583 / 0.0624 s |
| K1b 혼합 압축 | 0.1840 / 0.1546 s | 0.1681 / 0.1503 s |
| K5 해제 (예외 폴더) | 0.2113 / 0.2198 s | 0.2066 / 0.2123 s |

- 1스레드 Deflate 비용(`zipcost`, 혼합 세트)은 MSVC 555~596 ms, clang 530~558 ms였습니다.
- 대략 2~5% 빨라집니다. 게이트 판정은 그대로 미달입니다.
- **빌드 설정에는 넣지 않았습니다.** 넣으면 모든 빌드 환경(CI 포함)에 LLVM이 필요해지는데, 그에 비해 이득이 작습니다. 배포 빌드에서 쓰려면 위 환경변수만 주면 됩니다.

## 4. 시도했지만 넣지 않은 것

| 시도 | 결과 |
|---|---|
| mimalloc 전역 할당자 | 압축·해제 모두 변화 없음 |
| 압축 읽기 버퍼 스레드별 재사용 | 잡음 범위. rayon 작업 훔치기로 재진입이 생겨 그대로는 쓸 수 없음 |
| 텍스트 세트에도 매핑 쓰기 | 잡음 범위 |

| 해제를 폴더 단위 작업으로 분배 | 실제 해제에서는 변화 없음 (3.3) |

## 5. 다음 후보

- **K1b**: 같은 압축률에서 Deflate CPU를 약 40% 줄이는 인코더가 있어야 합니다. clang 빌드로는 2~5%만 줄어듭니다(3.4).
- **K5**: 파일 생성·시간 설정은 OS 비용입니다. 이 PC(물리 6코어, NTFS)에서는 2배 게이트가 측정 잡음에 따라 넘기도 하고 못 넘기도 하는 경계입니다.
