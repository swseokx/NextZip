브랜치 `v1-formats` (워크트리 `nextzip-v1-formats`). 스펙 3.1(만들기)·3.2(풀기)·9(보안)·11(로드맵)의 M3 항목.

## 풀기 포맷

검증 방법 약어: **F** = 회귀 픽스처(매니페스트의 이름·크기·CRC 일치, 격리 프로세스 경유 포함), **7** = 7-Zip 결과와 교차 확인, **G** = 생성기 테스트(우리가 만든 이미지), **C** = 코퍼스(libarchive / unarc-rs / 실사용 파일), **Z** = 퍼즈 타깃.

| 포맷 | 리더 | 격리 | 검증 |
|---|---|---|---|
| ZIP (Deflate/Store, AES, ZIP64) | nz-core | 아니오 | 기존 M0–M2 테스트, C, 7 |
| ZIP 확장 메서드 (LZMA, PPMd, BZip2, Deflate64, zstd, XZ — ZIPX) | unarc-rs → zip | 예 | F, 7, C, Z(zip7z) |
| 7z (LZMA/LZMA2, PPMd, BZip2, Deflate, Delta, ARM64, AES 등) | nz-core, 확장 코더는 unarc-rs → sevenz-rust2 | 확장만 예 | F, 7, C, Z(zip7z) |
| RAR 4 / 5 (분할 포함) | UnRAR C 라이브러리 | 예 | 기존 테스트, C |
| TAR, tar.gz / .xz / .bz2 / .lz4 / .zst | nz-core | 아니오 | 기존 테스트, C |
| ALZ, EGG | nz-core | 아니오 | 기존 테스트 + 알집이 만든 분할 ALZ 실물 샘플 (아래) |
| GZ, BZ2, XZ, LZMA, LZIP, ZST, LZ4, BR, Z (단일 스트림, 안의 tar 포함) | nz-formats stream | 예 | F, 7, C, Z(stream) |
| CPIO (bin LE/BE, odc, newc, crc), AR, DEB, RPM | nz-formats | 예 | F, 7, C, Z(package) |
| ASAR, XAR, UUE, XXE | nz-formats | 예 | F, C, Z(package) |
| MSI (CFB) | nz-formats (cfb) | 예 | 실사용 MSI 100+개, 7, Z(image) |
| ISO 9660 + Joliet | nz-formats | 예 | F, 만들기 왕복 테스트, Z(image) |
| VHD (고정/동적), VHDX, VMDK (sparse/stream-optimized), QCOW2 (일반/압축) | nz-formats vdisk | 예 | G (생성기 테스트 5개), Z(image) — 실물 이미지 미검증 |
| CAB (MSZIP, LZX) | unarc-rs (+ lzxd 패치) | 예 | F, 7, C, Z(legacy) |
| ACE, ARC/PAK, ARJ (분할 포함), ZOO, LHA/LZH, HA, UC2, SQ, SQZ, HYP, JAR(ARJ Software) | unarc-rs | 예 | F, C(unarc-rs 테스트 데이터), Z(legacy) |
| Amiga LZX, DMS, ADF, HDF, Pack-Ice/ICE | unarc-rs | 예 | F, C, Z(legacy) |
| Commodore D64, T64, Lynx, Atari ATR, FAT 플로피 | unarc-rs | 예 | F, C, Z(legacy) |
| SFX (PE/ELF 스텁 + 7z / RAR / ZIP), 앞에 쓰레기가 붙은 ZIP | 위 리더 + 오프셋 탐지 (이번에 추가) | 예 | libarchive SFX 6개 + 합성 SFX 테스트, C |
| `.001` 분할 세트 (ZIP, 7z) | Concat 리더 (이번에 추가) | 예 | `split_001_sets` 테스트, 7 |

레거시 이름 코드페이지: ZIP과 같은 방식으로 감지. LHA는 원시 바이트를 살려 Shift-JIS/CP949 감지(`lha_shift_jis_names` 테스트). ARJ·ZOO 등은 unarc-rs가 이름을 손실 변환해 원시 바이트를 얻을 수 없음 (남은 일).

CLI: `nz c -fmt:zipx|iso|gz|xz|bz2|zst|lz4|exe|sfx-x64|sfx-arm64` 또는 출력 확장자로 선택(`.exe` → 현재 아키텍처 SFX), ZIPX 메서드는 `-zm:`.

### EXE SFX

- 구조: `[nz-sfx 스텁 exe][7z][16바이트 트레일러 b"NZSFX\0\x01\0" + 7z 시작 오프셋 u64 LE]`. 스텁은 트레일러로 7z를 찾고, 7-Zip·NextZip 리더는 일반 7z SFX처럼 시그니처로 찾는다.
- 스텁(`crates/nz-sfx`): Windows 서브시스템, MessageBoxW UI(대상 폴더 확인, 덮어쓰기 확인, 완료). `-y`(묻지 않고 덮어쓰기), `-o:<폴더>`. 종료 코드 0 성공 / 1 오류 / 2 취소. 기본 대상은 `<exe 폴더>\<exe 이름>`.
- 보안: 모든 멤버 이름을 먼저 검사해 절대 경로·드라이브·`..`·금지 문자가 하나라도 있으면 아카이브 전체를 거부(리더 정책과 같음). 심볼릭 링크는 만들지 않음.
- 디코더: sevenz-rust2(기본 기능 끔 + `deflate`) → LZMA/LZMA2/BCJ/Deflate/Copy만. 그래서 SFX 페이로드는 zstd 대신 LZMA2로 강제.
- 만들기: 스텁의 PE COFF machine(0x8664 / 0xAA64)을 확인해 아키텍처가 다르면 거부. 스텁은 `nz.exe` 옆의 `nz-sfx-x64.exe` / `nz-sfx-arm64.exe`(설치 파일에 둘 다 포함, `build-installer.ps1`이 빌드·서명).
- 릴리스 스텁 크기: x64 595,456 B, ARM64 543,232 B. 예: 108,897 B 폴더 → SFX x64 600,530 B / ARM64 548,306 B.
- 테스트(`crates/nz-sfx/tests/sfx.rs`, 5개 통과): 스텁을 `-y -o:`로 실행해 원본과 바이트 비교, 덮어쓰기 거부, 아키텍처 불일치 거부, 손상 페이로드·트레일러 없음 오류, NextZip 리더·7-Zip 26.06 교차 확인. ARM64 SFX는 x64에서 실행할 수 없어 라이브러리·NextZip·7-Zip으로 확인(`NZ_SFX_ARM64_STUB`).
- 설치한 도구(사용자 허락): `rustup target add aarch64-pc-windows-msvc`, Visual Studio Build Tools 2022(17.14) 구성 요소 **`Microsoft.VisualStudio.Component.VC.Tools.ARM64`**(MSVC 14.44.35207 ARM64 빌드 도구; `setup.exe modify --add ... --passive --norestart`, 종료 코드 0).

## ALZ 분할 세트 실물 확인

- 샘플: 알집 12.38(설치 파일 `ALZip1238.exe`, altools.co.kr 공식 링크 → `aldn.altools.co.kr`, 44,816,088 B, 서명 ESTsoft Corp. / DigiCert 유효, SHA-256 `3C1A44AD…B5F6FC`)의 `ALZipCon.exe -a -v64KB`로 3볼륨(65,536 / 65,536 / 9,165 B) 생성. 한글 폴더·파일 이름(`src/한글/데이터.bin`) 포함. 최소 분할 크기는 64KB.
- 교차 확인: NextZip `nz l/x` 결과와 원본의 SHA-256이 같음(별도 225,850 B 3볼륨 세트로도 확인). **리더 수정 불필요** — `alz.rs`의 볼륨 처리(첫 볼륨 외 8바이트 머리, 마지막 외 16바이트 꼬리 제거)가 실물과 맞음.
- 실물 볼륨 구조: 둘째 이후 볼륨 머리 `ALZ\x01\x0a\x00` + u16 볼륨 번호, 마지막이 아닌 볼륨 꼬리 `CLZ\x01` + 0×8 + `CLZ\x03`. M2의 합성 분할 생성기는 볼륨 번호 0·꼬리 0으로 써서 외부 해제 도구가 볼륨 경계에서 실패했음 → 생성기를 실물 구조로 고치자 **합성 세트도 외부 도구 교차 확인 통과**(`alz_split`에 외부 도구 확인 추가).
- 회귀 테스트: `tests/data/alz_split_real.alz/.a00/.a01`(141 KB, NOTICE.md 기록) + `legacy.rs::alz_split_made_by_alzip`(NextZip으로 풀어 크기·CRC32 비교, `NZ_REF_ARCHIVER`가 있으면 외부 도구로도).
- 정리: 설치 파일은 알집 본체가 아닌 ALTools 매니저를 설치했고, 알집은 매니저에서 사용자가 직접 설치(제휴·광고·시작 페이지 항목은 사용자가 해제). 사용 후 알집·매니저를 제거 프로그램(`/VERYSILENT`)으로 제거. 설치 전 스냅샷과 비교한 결과:
  - 시작 프로그램(Run 키 3곳, 시작프로그램 폴더 2곳)·예약 작업·서비스(`ALUpdateService`)·프로세스: **남은 것 없음**.
  - 제거 프로그램이 남긴 것 → 직접 삭제: `Program Files (x86)\ESTsoft\Common`, `ProgramData\ESTsoft\ALZipPF`, `%APPDATA%\ESTsoft`, `%LOCALAPPDATA%\ESTsoft`, `%LOCALAPPDATA%\com.est.kestrel`(WebView2 캐시 8 MB), `%LOCALAPPDATA%\ECRSC`(빈 크래시 보고 폴더), `HKCU\Software\ESTsoft`, `HKLM\Software\WOW6432Node\ESTsoft`, `HKLM\Software\Classes\ALZip.ProtectedFolder`.
  - **파일 연결**: 설치 중 사용자 기본 앱(UserChoice) 20개 확장자(.zip .7z .rar .alz .egg .tar .gz .xz .bz2 .cab .jar .apk .arj .lzh .lha .tgz .tbz .tbz2 .uu .Z)가 ALZip으로 바뀌었고 제거 후에도 남음 → 사용자 허락을 받아 UserChoice 키 삭제, 설치 전 상태로 복구. 최종 스냅샷 차이 없음.
- 다운로드는 사용자 PC의 AdGuard가 `advert.estsoft.com`을 막아 사용자가 잠시 끄고 진행.

## 코퍼스 비교 (NextZip vs 7-Zip 26.06 포터블)

하네스: `bench/corpus/compare.py` — 두 도구로 풀고 성공 여부(종료 코드 0 + 파일 1개 이상)와 결과 트리(파일 수·크기·CRC)를 비교. 7-Zip이 한 겹만 여는 tar.* / RPM은 한 겹 더 풀어 비교.

| 코퍼스 | 파일 | NextZip 성공 | 7-Zip 성공 | 7-Zip만 성공 | NextZip만 성공 | 내용 차이 |
|---|---|---|---|---|---|---|
| 회귀 픽스처 | 71 | 69 | 44 | 0 | 25 | 1 |
| unarc-rs 테스트 데이터 | 129 | 105 | 37 | 0 | 68 | 1 |
| 실사용 (C:\Windows, Program Files의 cab/msi/gz/zip/jar/asar) | 141 | 141 | 137 | 0 | 4 | 9 |
| libarchive 3.8.11 테스트 파일 (수정 전) | 550 | 341 | 299 | 24 | 66 | 36 |
| libarchive (수정 후) | 550 | 352 | 299 | 15 | 68 | 36 |

실패 원인 해설:

- **픽스처·unarc-rs에서 NextZip이 못 푼 것**은 모두 의도된 실패: CRC 오류 샘플, 암호 걸린 샘플(암호 미입력), 분할 세트의 2번째 이후 조각, 아카이브가 아닌 파일(.COM, FILE_ID.DIZ), UC2 UltraCrypt. sqz 2건은 `../LICENSE` 경로라 보안 정책으로 거부.
- **실사용 내용 차이 9건**은 모두 MSI: 7-Zip은 MSI 안의 `Data.cab`을 펼쳐 보여주고 NextZip은 MSI 스트림 그대로(Data.cab 포함) 꺼냄. Data.cab을 다시 풀면 데이터 동일 확인.
- **libarchive 7-Zip만 성공 — 이번에 고친 것**: SFX 6개(7z PE/수정 PE/ELF, RAR4/RAR5, ZIP), 앞이 0으로 채워진 ZIP, zstd skippable 프레임 2개.
- **libarchive 7-Zip만 성공 — 의도된 실패 (4건)**: 절대 경로·`./`·`../` 멤버가 있는 `test_leading_slash.tar`, `test_patterns_2.tar`, `test_patterns_4.tar`, `test_compat_mac-2.tar.Z`. 보안 정책(스펙 9)상 아카이브 전체를 거부함 — **결정됨(2026-11-22, 통째 거부 유지)**. 7-Zip은 경로를 고쳐서 풂.
- **libarchive 7-Zip만 성공 — 남은 것 (범위 밖·업스트림, 11건)**:
  - nz-core tar 경로 3건(`tar_pax_negative_time` **패닉**, `tar_empty_with_gnulabel`, `tar_timestamp_overflow`), tar 크레이트 엄격성 1건(`gtar_redundant_L`) — nz-core 소관이라 손대지 않음. 패닉은 v1-perf 쪽에 전달 필요 (`crates/nz-core/src/tarfam.rs:974`).
  - 다중 캐비닛 CAB(`cab_multi.p1/p2`): unarc-rs 미지원.
  - `test_read_format_huge_rpm.rpm`: 헤더 index 수가 2³¹로 조작된 샘플 — 거부가 맞음.
  - 비표준 이름 RAR 분할(`*_aa`, `*_ab`) 3건, `test_compat_xz_1.txz`(잘린 tar) 1건.
- **libarchive 내용 차이**는 대부분 이름 코드페이지(cp866/koi8r/eucjp/cp932 — 7-Zip은 깨진 이름, Windows 대소문자 충돌), 심볼릭/하드 링크(7-Zip은 링크 생성, NextZip은 스펙 9에 따라 링크 미생성), 스파스 파일, 하네스의 겹 처리(.tgz/.tlz/.pax.Z) 차이.

| fmt_detect (5차) | 검사 켬, unarc 경로 제외 | **140,338** | **크래시 없음** (20분 완주) |

발견과 조치:

1. **VHD 길이 512 미만에서 뺄셈 오버플로 (우리 코드, `vdisk.rs`)** — 수정. 회귀 테스트 `every_format_rejects_tiny_input_cleanly`(모든 포맷에 0~4096바이트 빈/0xFF 입력을 강제로 넣어 패닉이 없는지) 추가.
2. **VMDK 용량(섹터 수 × 512) 곱셈 오버플로 (우리 코드, `vdisk.rs`, 1차 재실행에서 발견)** — 수정하면서 vdisk.rs의 파일 유래 산술을 전수 점검: VMDK grain·GD 오프셋 포화 곱셈, VHDX 메타데이터 영역이 32바이트 미만이거나 항목 수가 영역보다 클 때 슬라이스 범위 초과 가능성도 함께 수정. 회귀 테스트 `extreme_header_fields_fail_cleanly`.
3. **HA(HSC) 디코더 무한 루프 (unarc-rs 업스트림)** — 격리 프로세스는 멈춰도 부모가 영원히 기다리는 문제였음. 부모에 **무응답 감시**(프레임이 300초 동안 없으면 디코더 종료 후 오류) 추가, 대기 중에도 취소가 즉시 먹도록 변경. 회귀 테스트 `hung_decoder_is_killed`(입력 `fuzz_ha_hang.ha`, 제한 5초).
4. **HA 디코더 덧셈 오버플로 패닉 (unarc-rs `ha/hsc.rs:827`)** — 제품에서는 패닉 가드가 "damaged archive (decoder fault)" 오류로 바꿈. 회귀 테스트 `decoder_panic_is_an_error`(입력 `fuzz_ha_overflow.ha`). Windows의 libFuzzer는 Rust 패닉 되감기(SEH 예외) 자체를 크래시로 잡아 가드까지 갈 수 없으므로, 퍼징 하네스에서만 HA를 건너뜀(업스트림 수정 전까지).
5. **ARC Squeeze 노드 테이블이 잘렸을 때 인덱스 범위 초과 (unarc-rs `arc/unsqueeze.rs:24`, 릴리스에서도 발생)** — 격리 프로세스 안의 패닉 가드가 오류로 바꿈. 같은 조건의 ARC를 직접 만들어 회귀 테스트 `arc_squeeze_short_node_table_is_an_error` 추가 (Windows libFuzzer는 패닉 입력을 아티팩트로 남기지 못함).

**퍼징 운영 메모**: Windows의 libFuzzer는 Rust 패닉 되감기(SEH 예외)를 그 자체로 크래시로 잡아 제품의 패닉 가드까지 가지 못함. 그래서 unarc-rs 업스트림 패닉 하나가 퍼징 실행 전체를 멈춤. 대응: HA는 하네스에서 제외, `fmt_detect`는 unarc 경로 제외(우리 감지·리더 코드에 집중), `fmt_legacy`는 제품과 같은 `-O` 빌드. 업스트림이 고쳐지면 다시 넣을 것. **우리 코드에서 남은 미해결 크래시는 없음.**
