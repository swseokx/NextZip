# NextZip 1.0 최종 성능 측정 (2026-11-24, 브랜치 `v1-release`)

NextZip 1.0.0의 성능 KPI(K1~K9) 최종 측정입니다. 이 문서에는 NextZip 자체의 절대 수치(시간, MB/s, 압축률, 스레드 수, 메모리)만 싣습니다. 상대 게이트(K1, K1b, K2, K4, K5, K5b)는 같은 실행 안에서 비교 도구와 견준 결과로 판정했고, 비교 도구의 수치는 이 저장소에 싣지 않습니다.

## 1. 방법

- **도구**: `nz bench`. 케이스마다 자식 프로세스로 실행하므로 프로세스 시작·종료 비용이 포함됩니다. 워밍업 1회 뒤 7회 측정의 중앙값입니다(K3는 5회, K7은 3회). 해제 결과는 파일 수와 바이트 수로 검증했습니다(모든 케이스 `verified = yes`).
- **스레드**: 12 (K7만 1과 12).
- **실행 파일**: 릴리스 빌드를 스크래치 폴더로 복사해 실행했습니다. 막 빌드한 exe는 Defender 검사로 첫 실행들이 느려지기 때문입니다.
- **악성코드 검사(AMSI)**: 복사한 폴더에 `nz-decode.exe`가 없으므로 해제 후 AMSI 검사는 돌지 않았습니다. 이전 1.0 측정과 같은 조건입니다. 기본 설치에서는 검사가 켜져 있어 해제 시간이 이보다 깁니다.
- **부하 조건**: 측정 직전 5초 샘플에서 전체 CPU 3코어 미만이고, 1코어 이상 쓰는 단일 프로세스가 없을 때만 측정했습니다. 실제 값은 전체 0.21~0.58코어, 최대 단일 프로세스 0.43코어였습니다(`1.0-final/load.log`).
- **데이터셋**
  - 텍스트 세트: `text_processors`, 1,211개 파일, 28,712,178 B (27.38 MiB)
  - 혼합 세트: 전체, 1,444개 파일, 105,120,128 B (100.25 MiB)
- **원자료**: `bench/results/1.0-final/` (NextZip 행만).

## 4. 게이트별 상세

### 4.1 압축 (K1, K1b, K2, K4)

| 세트 | 케이스 | 크기 (B) | 압축률 | 압축 s (1차 / 2차) | 해제 s (1차 / 2차) | 최대 WS 압축/해제 MiB |
|---|---|---:|---:|---:|---:|---:|
| 텍스트 | zip:5 | 14,637,388 | 50.98% | 0.052 / 0.054 | 0.177 / 0.195 | 53 / 13 |
| 텍스트 | 7z:6 | 12,992,775 | 45.25% | 0.605 / 0.646 | 0.236 / 0.273 | 272 / 54 |
| 혼합 | zip:5 | 72,391,199 | 68.87% | 0.130 / 0.136 | 0.320 / 0.411 | 129 / 31 |
| 혼합 | 7z:6 | 65,505,923 | 62.32% | 1.701 / 1.738 | 0.429 / 0.431 | 586 / 193 |

- 7z 압축 시간은 이전 1.0 측정(텍스트 0.85~0.87 s, 혼합 2.78 s)보다 각각 약 28%, 38% 줄었습니다. 이번 브랜치의 기본값 변경(5장)과 더 조용한 측정 조건이 함께 반영된 값입니다.
- 압축률 조건(비교 도구 중 더 좋은 쪽 이하)은 두 세트 모두 충족했습니다. 기본값 변경으로 크기는 텍스트 +1,986 B(+0.02%), 혼합 +146,480 B(+0.22%) 늘었습니다.
- K1, K1b: 시간의 대부분이 파일 1,211~1,444개의 열기·읽기와 프로세스 고정 비용입니다(이전 보고서 6.5장). 이번에도 출력 파일 미리 확장(`set_len`)을 시험했지만 빨라지지 않아 넣지 않았습니다.

### 4.2 해제 (K5, K5b)

- K5 (Defender 켜짐, 혼합 ZIP): 0.320 / 0.411 s.
- K5 엔진 단독 (`C:\nzbench-excl` 예외 폴더): 0.191 s. 남은 시간의 대부분은 NTFS 파일 생성·쓰기·닫기입니다.
- K5b (7z): 혼합 0.429 / 0.431 s, 텍스트 0.236 / 0.273 s.

### 4.3 K3

- 7z -l:9 텍스트: 12,900,957 B (44.93%), 2.125 s = 12.9 MB/s. 기준(42.5%, 17 MB/s) 모두 미달입니다.
- 결정에 따라 표준 7z 코더만 씁니다. 텍스트 세트의 `.sla` 12.25 MB가 이미 zlib 스트림이라 표준 LZMA2로는 더 줄지 않습니다.

### 4.4 K6

- `tar.zst`(64 MiB 독립 프레임) 단일 파일 2,102,402,560 B → 예외 폴더, 5회: 0.757 / 0.744 / 0.753 / 0.756 / 0.756 s, 중앙값 0.756 s = **2.78 GB/s**. 이전 측정(2.08 GB/s)보다 높은 것은 측정 조건 차이이며 코드는 바꾸지 않았습니다.
- 병목 분석(이번 브랜치):
  - 쓰기 스레드가 전체 시간의 약 96%(875 / 913 ms) 동안 `WriteFile`에 있었습니다. 병렬 디코딩만으로는 4.5 GB/s가 나옵니다.
  - 쓰기 스레드를 2개·4개로 늘려 위치 지정 쓰기를 해 봤지만 1.8~2.1 GB/s로 더 느려졌습니다. 캐시 쓰기 경로 자체가 한계입니다.
  - 3 GB/s를 넘으려면 버퍼 없는 쓰기(DMA)나 출력 파일 메모리 매핑처럼 복사를 없애는 방식이 필요합니다. 1.0 이후 과제로 남깁니다.

### 4.5 K7

1스레드 → 12스레드 압축 배율 (3회 중앙값):

| 세트 | zip:5 | 7z:6 |
|---|---:|---:|
| 텍스트 | 0.235 → 0.057 s = 4.12배 | 2.829 → 0.587 s = 4.82배 |
| 혼합 | 0.593 → 0.129 s = 4.60배 | 8.244 → 1.737 s = 4.75배 |

물리 코어가 6개라 SMT를 더해도 이론상 최대가 약 7~7.5배입니다. 8배 기준은 물리 코어 12개 이상인 장비에서 다시 재야 합니다.

### 4.6 K8

`nextzip.exe --probe-startup` (프로세스 생성부터 첫 그리기까지), 각 15회:

| 시나리오 | 중앙값 | 범위 |
|---|---:|---:|
| 빈 화면 | 107.5 ms | 46.9~168.1 |
| 7z 열기 (혼합 세트 7z) | 135.5 ms | 78.1~220.6 |

열기 시나리오의 최댓값 하나가 200 ms를 넘었지만 중앙값 기준으로 충족입니다.

### 4.7 K9

`nz bench`가 자식 프로세스별 최대 commit을 기록합니다. NextZip 케이스 중 최댓값:

| 케이스 | 최대 commit (압축 / 해제) |
|---|---:|
| 텍스트 7z:9 (K3) | 806 / 59 MiB |
| 혼합 7z:6 | 802 / 250 MiB |
| 혼합 zip:5 | 145 / 32 MiB |

모두 1 GB(10^9 B = 954 MiB) 미만입니다.

## 5. 이번 브랜치의 변경

7z 레벨 6·7 기본값만 바꿨습니다. 다른 형식과 다른 레벨의 출력 바이트는 그대로이며, 7z 출력은 여전히 스레드 수와 무관하게 같습니다(기존 결정성 테스트 통과).

| 항목 | 이전 | 1.0 | 근거 |
|---|---|---|---|
| 기타(이미 압축된 스트림 등) LZMA2 | bt4, normal | hc4 normal, depth 2 | 단일 스레드 클래스 비용 −25~35%, 크기 +0.06%. bt4는 이 데이터에서 매치 파인더 캐시 미스에 시간을 씀 |
| 기타 세그먼트 / 프리로드 | 1 MiB / 1 MiB | 2 MiB / 512 KiB | 프리로드 처리 비용이 hc4 normal 인코딩과 비슷해 히스토리를 줄이는 쪽이 같은 크기에서 쌈 |
| x86 코드 nice | 128 | 64 | 크기 거의 같음(−120 B), CPU 약 −5% |
| ZIP 계열 컨테이너 zstd 레벨 | 12 | 9 | 혼합 세트에서 이 zstd 프레임이 핵심 경로. 단독 621 → 187 ms, 크기 +0.2% |

함께 넣은 것:

- CLI: x86 코드 전용 LZMA2 조정 옵션 `-emf`, `-enice`, `-edepth`, `-elc`, `-elp`, `-epb`, `-edict`.
- 예제 `classcost`: 한 클래스의 모든 세그먼트를 한 스레드로 인코딩해 크기와 CPU 시간을 잽니다. 병렬 실행 시간은 부하에 따라 크게 흔들려서, 설정 비교는 이 단일 스레드 값으로 했습니다.
- 버전 1.0.0 (워크스페이스, GUI·설치 프로그램 매니페스트, `nz` 도움말 첫 줄).

### 시도했지만 넣지 않은 것

| 시도 | 결과 |
|---|---|
| x86 코드 세그먼트 2048 KiB / 프리로드 4096 KiB | 핵심 경로는 짧아졌지만 총 CPU가 늘어 전체로는 느려짐 |
| x86 코드 hc4 normal, bt3 depth 8, depth 16~24 | 크기 +10~111 KB에 비해 이득이 작음 |
| 기타 클래스 bt3 depth 8 | 크기 −17 KB로 더 좋지만 시간 이득이 hc4 normal depth 2보다 작음 |
| 텍스트 depth 16 | +5 KB에 시간 이득이 잡음 수준 |
| ZIP 출력 파일 미리 확장 | 빨라지지 않음 |
| K6 쓰기 스레드 여러 개 (위치 지정 쓰기) | 더 느려짐 (4.4장) |
